# CLAUDE.md

**Granite Text Intelligence** — a Streamlit application for **summarization, topic, intent, and sentiment analysis** using IBM's [granite-4.2-3b](https://huggingface.co/ibm-granite/granite-4.2-3b) (the reasoning generation, run with thinking **off**) on Apple Silicon with MLX (`mlx-lm`). A single-shot playground: you provide text (paste, file upload, or a built-in sample), toggle which analyses to run, and get the results back. All four features are powered by prompting a single Granite model; the three classification features request JSON and are parsed defensively. Output can be localized to any of Granite's 12 supported languages (default: match the input).

## Rules

Each is justified in the section named. The reasons are non-obvious and were paid for in failures — read the justification before deciding an exception is safe.

- **Never hand-edit `uv.lock`** — regenerate it with `uv lock`; the hook blocks edits to it. → *Commands*
- **Bump `version` and run `uv lock`, then land *both* files.** A lone `pyproject.toml` bump fails CI at `uv sync --locked`, and no release is cut. → *Commands*
- **After a `uv lock --upgrade` that moves `mlx`, `mlx-lm`, `transformers` or `huggingface-hub` — or any change to `MODEL_NAME` or a prompt — run the smoke test by hand.** No test executes a line of `mlx`. → *Verifying a dependency upgrade*
- **Always pass `enable_thinking=False` to `apply_chat_template`, explicitly.** Granite 4.2 thinks by default and mlx-lm injects `enable_thinking=True` when the kwarg is omitted; a thinking run spends the whole JSON budget reasoning. → *Model*
- **Treat a ruff/ty major as its own reviewable change**, not incidental lockfile noise — a linter upgrade can redefine the gate with no code change. → *Commands*
- **Don't reword `language_directive` without re-running the A/B.** Clause order, the unquoted field name and the requirement stated at *both* ends are load-bearing — and "every sentence of it" must stay out, since under "Match input" it makes the model copy the input as its rationale. → *Design decisions (2026-08-12, 2026-09-21)*
- **Any future prompt A/B needs a meaningfulness check, not just a script check** — degenerate katakana still passes a CJK-codepoint test. → *Design decision (2026-08-12)*
- **Don't re-litigate tool-calling** without a material model/task change — and note the 4.2 swap *was* one; the decision now rests on the JSON path still working, not on the 4.1 corpus. → *Design decision (2026-06-05)*
- **A new test stub gets a new `$STUB_*` env var**, never a file written per test — that cost ~17 s of a 21 s gate. → *Tests*
- **Use Conventional Commits.** `release.sh --generate-notes` turns subject lines into public release notes. → *Commits*
- **A theme change keeps `[theme.light]` *and* `[theme.dark]`, and re-pins every sentiment `<color>TextColor` — plus yellow's — in both.** A lone `[theme]` block drops the appearance toggle silently; an unset `TextColor` is *derived* from its base color and washes the verdict out — derived yellow put `st.warning`'s light-mode text at **2.59:1**. → *Configuration*
- **The favicon is a vendored file, never a `:material/` shortcode** — the shortcode form is resolved by the frontend into a `fonts.gstatic.com` fetch. → *Configuration*
- **The Plex faces are vendored, not fetched.** A missing `static/fonts/*.woff2`, a `unicodeRange` dropped from a face, or `enableStaticServing` turned off all fall back to the bundled font **silently**. → *Configuration*
- **`baseFontSize = 15` is load-bearing, not taste.** It is what fits IBM Plex under the results-strip ceiling, and it rescales every rem figure in *Layout* with it — changing it means re-measuring them. → *Configuration*, *Layout*

## Commands

- **Lint**: `uv run ruff check .`
- **Format**: `uv run ruff format .` — reaches **Markdown as well as Python**: ruff ≥ 0.16 formats the code inside `python`-tagged fenced blocks, so a mis-spaced snippet in `CLAUDE.md` fails `--check` in CI exactly like a `.py` file would. **Formatting only** — `ruff check` skips Markdown outright (it reports "No Python files found" and exits 0), so an unused or unsorted import inside a fence is *not* linted. `README.md` is untouched today; its fences are all `bash`.
- **Typecheck**: `uv run ty check`
- **Test**: `uv run pytest`

All four live in **`scripts/gate.sh`**, which CI (`.github/workflows/ci.yml`) and the Claude Code Stop hook (`.claude/settings.json`) both invoke, so the two cannot drift. It runs the *verifying* variants (`ruff format --check .`, `pytest -q`), so it reports formatting drift rather than fixing it. Reproduce CI with **`GATE_FORCE=1 ./scripts/gate.sh`** — a bare `./scripts/gate.sh` skips a tree that already passed (see the memo below), which reproduces the Stop hook but not CI. Run the individual commands above while iterating on one gate.

**Releasing** is a side effect of merging, not a command: bump `version` in `pyproject.toml`, run **`uv lock`**, and land **both files** on `main`. Once the gate is green CI runs `scripts/release.sh`, which tags `v<version>` and publishes a release with generated notes; every other push is a no-op.

`uv.lock` records the *project's own* version, so the two files move together. This is easy to half-do and the failure is quiet: a commit carrying only `pyproject.toml` fails CI at `uv sync --locked`, and since `release` needs `check`, no release is cut — it looks like the automation stopped working. Nothing local catches it, and the reason is worth knowing: every gate command runs under `uv run`, which **silently re-locks** before the command starts, so the working tree always looks consistent no matter what is staged (verified — a bump to `0.2.0` had rewritten `uv.lock` before pytest imported, and reverting `pyproject.toml` rewrote it back; one such relock also quietly dropped an `mlx-metal` platform marker). **That marker drop is benign, and it recurred on the 0.2.0 bump** — worth knowing before someone treats it as a corrupt lock: `uv` removes `platform_system == "Darwin"` from *inside* `mlx`'s dependency list because `mlx-lm` already requires `mlx` under `sys_platform == 'darwin'`, so within that subtree the condition is always true. The effective gating survives — `uv export` still emits `mlx-metal==<locked version> ; sys_platform == 'darwin'` (verified 2026-08-15 on 0.32.0, and again on 2026-09-21 when the `uv lock --upgrade` to 0.32.2 dropped the marker a third time), which is the check to run if it happens again rather than reading the lock diff alone. Running `uv lock` explicitly makes the update deliberate and visible before you stage rather than a side effect you might not commit. `uv.lock` is on the hook's blocked-edit list, so regenerate it — never hand-edit it.

Running the script by hand is idempotent and refuses to tag a commit that isn't on `origin/main`, but it is not a dry run — on an untagged version bump it publishes for real.

No dev tool carries a version constraint in `pyproject.toml`. `uv.lock` still pins exact versions and CI runs `uv sync --locked`, so any given build is reproducible — but nothing bounds what the *next* `uv lock --upgrade` pulls in, which means a **linter upgrade can redefine the gate without a line of our code changing**: ruff 0.16 expanded its default rule set (see Error Handling for the `BLE001` fallout) and widened the formatter to Markdown, both of which landed as gate failures on a routine `uv lock --upgrade`. Treat a ruff/ty major as its own reviewable change rather than incidental lockfile noise. For ty, "major" undersells it: it is pre-1.0 and promotes **warn-by-default, stable** rules in patch releases — `redundant-condition` in 0.0.79, `truthiness-test-of-callable` and `truthiness-test-of-iterable` in 0.0.83 — and `ty check` exits 1 on a warning, so each such release widens the gate. The 2026-09-21 move from 0.0.71 to 0.0.83 added those three; they happen to be clean on this tree, which is a fact about the tree, not about the upgrade. `ruff check --preview .` and `ruff format --check --preview .` are the early warning for the next ruff minor (the preview formatter style `hug_parens_with_braces_and_square_brackets` would already touch three call sites in `streamlit_app.py`).

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

## Verifying a dependency upgrade

Four green gates say nothing about `mlx`: every test mocks at the `mlx_lm` boundary, so no test executes a line of the compute library (see Tests). After a `uv lock --upgrade` that moves `mlx`, `mlx-lm`, `transformers` or `huggingface-hub`, after any change to `MODEL_NAME`, and after any prompt change, run the model by hand against the warm local cache:

```bash
HF_HUB_OFFLINE=1 uv run python - <<'PY' 2>&1 | grep -v ScriptRunContext
import streamlit_app as app
from mlx_lm import load

model, tok = load(app.MODEL_NAME)
for name, text in app.SAMPLE_TEXTS.items():
    for lang in (app.LANGUAGE_ENGLISH, "German", "Japanese", app.LANGUAGE_AUTO):
        for f in app.FEATURES:
            r = app.run_feature(f, text, model, tok, language=lang)
            ok = "prose" if f["output"] == "prose" else ("parsed" if r["parsed"] else "PARSE FAIL")
            shown = r["raw"] if f["output"] == "json" else r["raw"][:150]  # 4.2 pretty-prints JSON; a prefix hides labels 3–5
            print(f"{name:15} {lang:11} {f['key']:9} {ok:10} {shown!r}", flush=True)
PY
```

Importing the module in bare mode runs the UI block harmlessly — widgets return defaults and Run is `False`, so nothing infers until the loop calls `run_feature` directly; the Streamlit warnings it prints are expected. It takes about three minutes on an M2 Max (48 runs at 1–4 s each). **Pass criteria:** all four features return sensible output, **all 36 JSON runs parse**, **no `<think>` or `</think>` appears in any `raw`** (a leak means `enable_thinking=False` was lost), **no `rationale` is a copy of the input** (the "Match input" rows are where that shows — see the 2026-09-21 design decision), and the German and Japanese runs localize their `rationale` *and* their topic labels into meaningful text while keeping the JSON keys and the `sentiment` enum in English. Two known 4.2-3b quirks are not failures: one label in the Product review's German topic set comes back garbled (`Batteriezahle`; the whole set turning to garbage, or katakana that is not a word, *is* a failure), and a `�` standing in for a rare kanji in a Japanese rationale (`�慮`, `�懸念` — seen in the News excerpt) is the model emitting an invalid byte sequence, verified by re-decoding the token ids, not a detokenizer bug. Two limitations sit outside the snippet's loop and are the model's, not the prompt's (both recorded in the 2026-09-21 design decision): a **Japanese** input under "Match input" comes back in English, and a short **German** input under "Match input" can get a summary that near-copies it (five sentences in, "3–5 sentences" asked for); an explicit language selection localizes both. A German object truncated mid-parse is the specific failure `_effective_max_tokens` exists to prevent, and degenerate-but-parseable labels are the failure the prompt A/B exists to prevent — so read the output, don't just count parses. Cold download and `HF_TOKEN` auth stay unexercised either way; a warm-cache run says nothing about them — and since huggingface-hub 1.32.0 a fresh Xet download lands in a cross-repo `hub/blobs/<prefix>/<xet-hash>` store reached through a second symlink hop from `snapshots/` (opt out with `HF_HUB_DISABLE_SHARED_BLOBS=1`), so a two-hop chain on a new machine is the new layout, not a corrupt cache; the existing single-hop cache still resolves offline.

## Dependencies

- `mlx-lm` (pinned `>=0.31,<0.32`) — model loading and generation on Apple Silicon; mlx and transformers are transitive deps. The `<0.32` cap guards against API drift, since decoding params pass through `generate(**kwargs)` rather than typed parameters; exact reproducibility is handled by `uv.lock`.
  - **The cap binds `mlx-lm`, not `mlx`.** mlx-lm declares `mlx` with a floor but *no upper* bound (`mlx>=0.31.2`), so the compute library floats free of the guard above — and since 0.31.3 is mlx-lm's latest release, the cap is not currently binding on anything. As of 2026-09-21 the lock pairs mlx-lm 0.31.3 with mlx 0.32.2 (0.32.0 from 2026-08-13 until that day's `uv lock --upgrade`), a combination newer than anything upstream shipped together (the mlx-lm sdist predates every mlx 0.32.x). That pairing is **verified by real-inference smoke test**, not by CI (re-verified 2026-08-14; again 2026-09-21 on granite-4.2-3b — whose MLX conversion IBM itself produced with mlx-lm 0.31.3, per the `*-metadata.properties` file in the repo; and once more the same day after the relock to mlx 0.32.2 / transformers 5.17.0 / tokenizers 0.23.2 / huggingface-hub 1.32.0 — 48/48 runs, 36/36 parses, no `<think>`, both documented blemishes reproduced byte-for-byte, and all 16 rows that have a 0.32.0 baseline identical). That relock also got a check the snippet cannot give: a live `streamlit run` session with **two** Run clicks and the Topics tab opened, because the smoke test runs on the main thread and never renders, while mlx 0.32.1 reworked the compile-cache's thread-local state (ml-explore/mlx#4248, fixed up in 0.32.2) under mlx-lm's `mx.compile`d `swiglu`, and pyarrow 25.0.0 segfaulted in exactly Streamlit's exited-script-thread-then-allocate pattern (apache/arrow#50471) — the second click is the one that runs on a fresh thread after the first has exited. Reading the 0.32.1/0.32.2 release notes is not a substitute: the two kernels that sound relevant (bf16 `gemv_wide`, the gqa-8 decode path) are dispatch-gated off this model — M3+ GPUs and 2–15 rows for the first, `gqa_factor == 8` for the second, and Granite 4.2-3b is 40:8 = 5 on an M2 Max — so only the run itself could show the outputs unchanged. One more thing worth knowing: the 4.2 MLX repos declare `tokenizer_class: "TokenizersBackend"`, a **transformers 5-only** class — under transformers 4.x `AutoTokenizer` cannot load the tokenizer at all (verified against 4.57.1). The floor is already implied by the `mlx-lm>=0.31` pin (every 0.31.x declares `transformers>=5.0.0`), so the lock merely records it; the point is that a transformers downgrade would break model loading outright, not subtly.
  - The test suite structurally **cannot** cover this. Every test mocks at the `mlx_lm` boundary (see Tests), which is the right call — real inference in CI would mean a 7.3 GB download per run — but it means no test executes a line of `mlx`; the only real contact in CI is the module-level `from mlx import nn`. Hence the hand-run in *Verifying a dependency upgrade*, which is not optional after a move to any of these four packages.
- `streamlit` (pinned `>=1.57`) — web UI. **The floor is still not argued from the theme.** The IBM Carbon theme restored on 2026-09-22 needs per-mode `[theme.light]`/`[theme.dark]` (**1.51.0**) and `metricValueFontSize`/`metricValueFontWeight` (**1.55.0**) — its newest requirement, checked against the release notes, and under the floor; every other key it sets (`baseFontSize`, `headingFontWeights`, `showWidgetBorder`, `showSidebarBorder`, `codeTextColor`, `dataframe*`, the `<color>TextColor` variants, `[theme.sidebar]`, `baseRadius`, `linkUnderline`, `codeFont`, and `[[theme.fontFaces]]` with `weight`/`unicodeRange` at **1.46.0**) is 1.47.0 or older, as is `server.enableStaticServing`. So the theme does not move the floor; what does need a recent Streamlit is `width="stretch"` (on `st.text` in `_preview` and `render_result`; the Run button dropped it for its natural width on 2026-09-21), the Material Symbol icons, `st.container(height=…)`, `st.container(horizontal=True, vertical_alignment=…)` (the Run row — horizontal flex containers landed in 1.48.0, per the 2025 release notes), `st.text(…, width=…)` and `st.code(…, language=None, wrap_lines=True)` — all of which predate `1.57` (verified). `st.sidebar` itself is ancient. Two sidebar options the layout could use and deliberately does not: `initial_sidebar_state="locked"` landed in **1.59.0** and the integer sidebar width is documented on 1.64 but absent from the 2025 and 2026 release notes, so both are post-floor — adopting either means raising `>=1.57`, not just adding to this list. Keep this list in step with the app: the procedure below says to check "the APIs above", so an API added to `streamlit_app.py` and not added here is one nobody checks. Nothing tests the lower bound — CI installs the `uv.lock` pin — so the floor is kept rather than lowered on the argument that an unverified bound is safer than a guessed one, not because `1.57` is known to be required. Anyone lowering it should check the APIs above against the target version by hand. Exact version pinned by `uv.lock`. One transitive fact belongs here rather than in the lock diff: **pyarrow 25.0.0 segfaults in exactly Streamlit's script-thread pattern** (first `import pyarrow` on a script thread that then exits, next rerun allocates — apache/arrow#50471, streamlit/streamlit#16111), which is why 1.61.1 capped `pyarrow<25` and 1.62.0+ declares `pyarrow!=25.0.0,<26`. The 2026-09-21 lock carries 25.0.1, admissible only because streamlit moved to 1.64.0 in the same relock; a lock that pairs an older streamlit with any 25.x will not resolve, and the app's `st.dataframe` topics branch is the one call site on that path. Until 2026-09-21 no test executed it — the UI suite's mocked `generate` returned a sentiment payload for every feature, so the Topics tab always rendered "No topics found." — which is what `test_topics_tab_renders_a_dataframe` now exists for (see Tests).
- `python-dotenv` (pinned `>=1.2.2`) — loads `HF_TOKEN` (and other env vars) from `.env` for local development

## Configuration

`pyproject.toml` — ruff lint (`extend-select = ["I"]` turns on isort import sorting atop ruff's defaults; `combine-as-imports`), pytest (`pythonpath`), ty (`python-version = "3.12"`)

`LICENSE` — Apache-2.0 for the project's **code**, declared to tooling in `pyproject.toml` via PEP 639 SPDX fields (`license`, `license-files`) and summarized in the README. The IBM Granite model is licensed separately (also Apache 2.0) and downloaded at runtime, not vendored here. The **IBM Plex** font files under `static/fonts/` *are* vendored and carry their own license — SIL OFL 1.1, whose terms require the notice to travel with the files, hence `static/fonts/LICENSE.txt`. The Material Symbols favicon under `static/icons/` is vendored too, under Apache-2.0 like the project itself. Both notices are entries in `license-files`, and both are named in the README's License section.

`README.md`, `docs/images/` — the user-facing README restates facts this file also carries (the model id and its weight sizes, the `granite-4.2-3b-q4-mlx` / `-q8-mlx` fallbacks for smaller machines and the `-8b-*` swaps for larger ones, the ~16 GB unified-memory envelope, the ~80 KB/token KV figure, the input precedence, all 12 language names) and embeds `screenshot-dark.png`, whose alt text pins a specific UI state. **No test guards any of it**, so a change to the model, the language list or the layout has to be mirrored there by hand, and a theme or layout change dates the screenshot. A `screenshot-light.png` shipped beside it until 2026-08-14, when removing the IBM Carbon theme dated both; the dark one was re-captured under the built-in dark theme and the light one was dropped rather than re-shot, so the README now carries a single image. It was re-captured again on 2026-08-15, when `layout="wide"` and the preview containers dated the previous one; the geometry moved with it, from 792 CSS px to **1000**. A **model change dates it too**, because the rationale in the image is model output: the 2026-09-21 swap to granite-4.2-3b left the alt text true (still `positive` / 0.95 under greedy decoding) but changed the pictured rationale, so it was re-captured a third time on 4.2 (2000 × 1572 px; the 4.2 rationale is shorter). The **sidebar layout** dated it a fourth time the same day, and it was re-captured with the sidebar in frame (2000 × 1588 px — the stacked main area is taller than the old columns, the rationale is unchanged). Restoring the **IBM Carbon theme** dated it a fifth time on 2026-09-22: re-captured at 2000 × **1512** px (the 15 px root makes the same content shorter), again from a real model run, with the alt text still true — `positive`, 0.95, and byte-for-byte the same rationale. The README's feature list names the theme, so a theme change edits that line too.

To reproduce it — or to add a light counterpart back — drive a headless Chrome over CDP rather than resizing a window (Chrome refuses to resize a maximized window, and a DPR-1 display cannot produce a 2× capture any other way). Set `Emulation.setDeviceMetricsOverride` to **1000 CSS px × `deviceScaleFactor` 2** (= its 2000 px), load `?embed=true&embed_options=dark_theme,show_padding` — that one URL selects the dark theme *and* hides the toolbar while keeping normal padding, and it **keeps the sidebar expanded** at 1000 px (`aria-expanded="true"`, 300 px; verified 2026-09-21), so the settings appear in frame without an extra click. `dark_theme` still resolves to the **custom** `[theme.dark]` once one ships — re-verified 2026-09-22, app background `rgb(22, 22, 22)` and the black sidebar rail. Its `light_theme` counterpart, however, did **not** switch a loaded page in testing; use CDP's `Emulation.setEmulatedMedia` with `prefers-color-scheme` if a light capture is ever needed — then click through Sample → Product review → Run → the Sentiment tab. Greedy decoding makes this reproducible: the Product review sample returns `confidence: 0.95` and the same rationale every time, which is what keeps the README's alt text true.

Four details are load-bearing, and each one cost a failed run:

- **The width is now an aesthetic choice, not a floor.** It was a floor while the columns were an even split — the result-tab strip clipped below ~930 CSS px, which the old 792 recipe did not clear even under `layout="wide"`. The 2:3 split removed that threshold and the full-width panel keeps it removed with the sidebar open (see Architecture): at 1000 px the sidebar takes 300 and the content gets 540, the title still fits on one line, and the strip has 163 px to spare, so 1000 is kept for the framing rather than because anything breaks below it.
- **The height cannot come from `document.scrollHeight`.** Streamlit scrolls an inner container, so the document stays exactly viewport-tall and reports back whatever height you asked for — a full-page capture silently returns just the visible window, and a too-tall viewport returns acres of dead space. Measure the lowest `getBoundingClientRect().bottom` among `[data-testid="stMainBlockContainer"]`'s children, then re-apply the override at that height. The sidebar is shorter than the main area (its content ends ~410 px down), so it never sets the height.
- **Do not poll `document.body.innerText` to detect that the run finished.** `innerText` omits subtrees that are not rendered, and every result tab except the active one is hidden — so waiting for the sentiment caption while `JSON` is the active tab waits forever, on a run that has already completed. Poll for elements instead (`[data-testid="stMetricValue"]`), which `querySelectorAll` finds regardless of visibility.
- **Match click targets on the *end* of `innerText`.** The Material Symbol ligature renders as a text prefix, so the Run button reads `"play_arrow Run"`, not `"Run"`.
- **Click with `Input.dispatchMouseEvent` at the element's centre, not `.click()`, and select tabs by `[data-testid=stTab]`.** Streamlit's tabs are `div[role=tab]` (there is no `button[role=tab]`), and a synthetic `.click()` on them selects nothing; the sample picker is `[data-testid=stButtonGroup]`. Add the block container's `padding-bottom` to the measured height, or the capture crops at the content edge and the one-pixel overflow summons a scrollbar that narrows the content (found on the 2026-09-21 recapture).

`static/fonts/` — the six vendored IBM Plex woff2 files plus the OFL license text, served at `/app/static/fonts/…`. **Four silent-failure modes live here**, each pinned by `TestThemeConfig` and each verified by mutation: a renamed or missing file, `server.enableStaticServing` turned off, a dropped `unicodeRange`, and a mis-cased key inside a `[[theme.fontFaces]]` table. The first two 404 every URL; the third never fetches latin-ext; the fourth makes Streamlit discard that face while logging a warning. All four end the same way — the browser falls through the family stack to the bundled Source Sans with no error, so the only symptom is that the app stops looking like IBM.

`static/icons/psychology.svg` — the favicon, and the last third-party request removed. `page_icon=":material/<name>:"` is resolved in Streamlit's **frontend**, which maps it to a `https://fonts.gstatic.com/s/i/short-term/release/materialsymbolsrounded/<name>/default/24px.svg` URL — so the shortcut form fetches the app's icon from Google on every cold load, while the Material Symbols *font* every icon in the UI uses is bundled. Handed a path, Streamlit inlines the file as a base64 `data:` URI (verified: `_get_favicon_string` returns `data:image/svg+xml;base64,…`), costing no request and working offline. The file is the same upstream glyph with one modification, `fill="#0f62fe"`: Material Symbols SVGs declare no fill, so the icon defaults to black and all but disappears on a dark browser tab strip. Apache-2.0, like this project — `static/icons/LICENSE.txt` records the origin and the edit.

Three things here are silent when wrong, and `TestPageIcon` pins each: a missing file (`set_page_config` swallows the error, the frontend's request 404s, the tab is simply iconless), a path resolved against the **working directory** instead of `Path(__file__).parent` (`streamlit run /abs/path/streamlit_app.py` can be launched from anywhere — this is why `_PAGE_ICON` is absolute), and the call site reverting to a shortcode. That last one is why the test **reloads the module under a spy** and resolves whatever was actually passed: an earlier version asserted on the `_PAGE_ICON` constant alone and the revert-to-`:material/` mutation sailed straight through it, since the constant still existed and still resolved.

`.python-version` — pins the project interpreter to `3.12` (via `uv python pin`), which `uv sync` / `uv run` honor automatically. Keeps the version you run and test against aligned with the `requires-python = ">=3.12"` floor and the ty type-check target, instead of letting uv auto-select the newest installed Python (e.g. 3.13).

`scripts/gate.sh` — the four Commands in one place, invoked by both CI and the Stop hook. Its header comment argues each point at length; four properties are load-bearing, each pinned by an *executing* test in `TestHooksConfig` because source-level substring checks proved too weak to catch a mutated failure path (see Tests):

- **Exits `2`, not `1`.** Claude Code treats only `2` from a hook as blocking; `1` — what ruff, ty and pytest all actually return — is a *non-blocking* error that lets the turn end on a red gate. Any non-zero fails a CI job, so one convention serves both callers.
- **Reports on stderr**, the stream fed back on a block, while ruff and pytest print diagnostics to stdout. An empty capture (OOM kill, hook timeout, half-created `.venv`) is replaced with a message naming the exit code.
- **Runs every gate even after one fails**, so a single block names everything that is wrong. Claude Code stops honoring a Stop hook after 8 consecutive blocks (raise with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`), and spending that budget one diagnostic at a time wastes it.
- **Skips only a tree that already passed** — a SHA-256 over `git ls-files -co --exclude-standard` against `.git/gate-ok`, written only on green: ~0.09 s for a turn that changed nothing against ~5.2 s for the full run. Every uncertainty runs: an empty file list, a missing memo, a red previous run, a non-empty `GITHUB_ACTIONS`, or `GATE_FORCE`. See the Stop-hook discussion below for why a *content* hash succeeds where `git status` and `stop_hook_active` both failed open.

It also `cd`s to `git rev-parse --show-toplevel` first: `ruff check .` and `pytest` resolve from the working directory, so a caller in a subdirectory would otherwise gate a narrower tree than it believes.

`scripts/release.sh` — cuts the GitHub release when `pyproject.toml`'s version has no tag yet, invoked by ci.yml's `release` job. It is a script rather than inline YAML because an escaped one-liner can't be run or tested, and this one has failure modes worth testing; `TestReleaseWorkflow` pins each property below by executing it with `gh` and `uv` stubbed. Its governing rule is that **every uncertainty is a refusal** — the artifact is a public tag people install, so guessing is never the cheaper option. The header comment argues each of these; what must stay true:

- **The trigger is "no tag exists for this version", not "pyproject.toml changed in this push".** A diff-based trigger has no correct answer to *changed since what?* (`github.event.before` is all-zeros on a branch's first push, a squash-merge rewrites the range, a re-run sees no diff at all), while the tag lookup makes re-runs, force-pushes and manual invocations converge. Exits `0` both when it releases and when there is nothing to release; plain `exit 1` on failure, **not** gate.sh's `2` — that 2 is a hook contract and this is not a hook.
- **The probe is `git/ref/tags/<tag>` (singular), and only a definite 404 may proceed.** The plural `git/refs/tags/<tag>` prefix-matches — verified against the live API, it returns **200** for `v0.1` off the existing `v0.1.0`, so a bump to `0.1` would report itself already released and silently never ship. It must ask the *remote* (the depth-1 checkout has no tags to find), and since a rate limit, an expired token and a 5xx all fail identically to a 404, the script matches `(HTTP 404)` in the response rather than trusting the exit status.
- **Draft first, publish second — then adopt, never duplicate.** The tag comes into existence only at publish, so nothing can leave a tag with no release — which the probe would read as "already released" and skip **forever, silently**. The symmetric hazard is real and was initially documented wrong: GitHub *accepts* a second draft for the same `tag_name` (a draft has no tag to collide with), so a failed publish does **not** fail loudly next time — it would leave two drafts racing for one tag, `gh release edit` resolving whichever it found first. The script therefore lists drafts before creating and adopts an existing one, retargeting it to *this* run's commit.
- **The version comes from `uv version --short`**, a real TOML read rather than a regex. `--short` is load-bearing (bare `uv version` prints `<name> <version>`; before uv 0.7 it printed uv's *own* version, now `uv self version`). The guard rejects any character with no business in a tag, not merely a bad leading one — a first-character-only test admits `0.1.0 (from pyproject.toml)` and would tag it verbatim, spaces and all.
- **A hand-run off `main` is refused.** Unless `GITHUB_ACTIONS` is exactly `true`, the target must be an ancestor of `origin/main`: outside Actions the workflow's `if:` is not in play and `HEAD` is whatever branch the caller is on, so a local run could publish a public tag pointing at an unreviewed commit. Inside Actions the workflow has already made that guarantee, and `origin/main` may not even be fetched at depth 1.

`--target` is `$GITHUB_SHA` (falling back to `HEAD`), so the tag lands on the commit the gate actually validated rather than on whatever the branch drifted to mid-run; an unresolvable commit is an error, because `gh` reads an empty `--target` as "use the default branch". Both `gh` and `uv` are checked for up front so a missing one is named instead of surfacing as a mis-attributed "could not read a version". It `cd`s to the repo root like gate.sh, since `uv version` reads `./pyproject.toml` and `gh` infers the repository from the working directory's remote unless `GH_REPO` is set (the workflow sets it) — and that anchoring block is duplicated rather than shared: extracting it would mean editing a Stop hook whose own failure path is separately pinned, for twelve lines.

Neither script is shellchecked by any gate — `scripts/gate.sh` runs four Python gates and reads no `.sh` file. Both were run through `shellcheck` and `actionlint` by hand; if that matters going forward it needs to become a fifth gate, not an assumption.

`.github/workflows/ci.yml` — GitHub Actions CI, two jobs. `check` runs `scripts/gate.sh` under `uv sync --locked` on every push to `main` and pull request, on a `macos-26` (Apple Silicon) runner — required, since `mlx`/`mlx-metal` are `sys_platform == 'darwin'` in `uv.lock` and `streamlit_app.py` imports `mlx` at module top, so a Linux runner couldn't even collect the tests. The label must stay inside `TestCIWorkflow.APPLE_SILICON_RUNNERS` (`macos-latest` / `macos-15` / `macos-26`) — an explicit **allow-list**, not a glob or a `>= 14` floor: that form is what stayed green on `macos-14` right through the image's deprecation, and it admits the x64 `macos-*-intel` / `macos-*-large` labels where the arm64-only mlx wheels don't install at all. When an image retires, move the label and the allow-list forward together; don't widen it back into a floor. Both jobs pin `actions/checkout@v7` and the **full** `astral-sh/setup-uv@v10.0.0` — setup-uv publishes no major or minor tags from v8 on, so `@v10` does not resolve. `release` then runs `scripts/release.sh`, `needs: check` (a tag never points at a red build) and `if: push && refs/heads/main` (a pull request, including a fork's, can't release — the version bump has to land first). It sits on `ubuntu-latest`, which is fine precisely because it only reads a TOML field and calls the GitHub API, never importing `mlx`. Workflow permissions are `contents: read`; **only** the release job widens to `contents: write`, keeping the job that executes a fork's code unable to push a tag. Its `concurrency` group never cancels in flight — cancelling can land between the draft and the publish, stranding a draft that blocks every later release. `TestCIWorkflow` and `TestReleaseWorkflow` guard this config against drift.

`.claude/settings.json` — project-shared Claude Code hooks: `ruff check --fix` on each edited `.py` followed by `ruff format` on `.py` **and** `.md` (lint is a no-op on Markdown; the `.md` branch exists because ruff ≥ 0.16 made doc snippets a formatted artifact CI enforces), a guard blocking edits to `.env` / `.env.*` (the committed `.env.example` is exempt so the template stays editable) / `secrets.toml` / `uv.lock`, and `scripts/gate.sh` on Stop. Personal overrides go in the gitignored `.claude/settings.local.json`.

Both hooks parse their payload with **`jq`**, an undeclared dependency that nothing installs. macOS 26 ships it at `/usr/bin/jq`, which is why this has never bitten — but if it is missing the guard **fails open**: `jq` not found writes to stderr and exits `0`, and the `.env` edit proceeds (verified). The guard is scoped `Edit|Write|MultiEdit` and does not cover `Bash`, so it is an accident guardrail, not a security boundary — its own message says so.

**Lint-fix runs before format, and the order is load-bearing** — it is ruff's own documented arrangement, for a reason that bites here specifically: `ruff check --fix` can *produce* unformatted code, and the formatter is what cleans it up. Deleting a module's last import (`F401`, a default rule) strands the two blank lines that followed it, so format-then-fix leaves a file starting `\n\ndef …` that `ruff format --check` rejects. That was the shipped order, and its failure was silent in the worst way: `ruff check --fix` exits `0` when it fixed everything, so the hook reported success and handed the Stop gate a formatting failure on a file it had just declared clean. Verified against ruff 0.16.2, and again against 0.16.8 on 2026-09-21 (same residue, same exit codes) — reversing the two is the whole fix.

Both commands run **even when the first fails**, accumulating into an `rc` rather than exiting early, for the same reason `gate.sh` runs every gate: one report should name everything that is wrong. Under the old early-exit form a `ruff format` failure skipped the linter entirely, and putting lint first without this would have let an unfixable lint error leave the file unformatted too — trading one dropped gate for another. Each command still checks its own exit status separately; chaining them so one status is discarded silently swallows `ruff format` I/O errors.

The format hook exits `2` on ruff failure for both extensions. On `PostToolUse` that does **not** block the edit — the tool has already run and the event cannot block — it only guarantees the diagnostic reaches Claude, which a bare exit `1` does not, since ruff writes to stdout and only stderr is fed back. Note that no literal `exit 2` survives in the command (`rc=2` … `exit $rc`), which is why `TestHooksConfig` pins that contract by *running* the hook rather than grepping it.

The Stop hook skips the gate only when re-running it is **provably redundant** — when every file the gate reads is byte-identical to a tree that already passed (mechanism in the memo bullet above).

Two cheaper short-circuits were tried first and both **failed open**, because each inferred "nothing to check" from a *proxy* rather than from the gate's inputs: an empty `git status --porcelain` skipped exactly the turns that had just *committed* work (committing clears dirtiness without clearing risk, and a held `index.lock` disabled the gate outright), and honoring `stop_hook_active` made it one-shot — it blocked once, then let the next Stop through without re-running anything, never verifying its own fix. (That flag is the right guard for a hook that *injects* work and the wrong one for a hook that *verifies*; the built-in 8-block cap already bounds the loop.)

A content hash has neither shape: committing does not alter file *content*, so skipping is correct, and nothing is recorded on a red gate, so it re-runs until green and verifies its own fix by construction. It also beats the tempting marker-file variant (PostToolUse writes "dirty", Stop reads it), which fails open on every edit that bypasses a tool hook: `sed -i`, `git checkout`, applying a patch.

Every uncertainty runs the gate, and two details are load-bearing:

- **An unreadable tree must not fall through to `shasum` of nothing.** That is `e3b0c442…`, a stable *non-empty* hash that could match a stored one — verified: running the fingerprint outside a git repo produces exactly it. An empty file list is therefore a refusal, not an answer, and the pipeline is `</dev/null` so `xargs` cannot block if it invokes `shasum` with no arguments.
- **The memo is recorded *after* the run, not before.** Every gate command goes through `uv run`, which silently re-locks, so `uv.lock` can differ by the time the gates finish; storing the pre-run hash would never match the tree the next Stop sees and the memo would never once hit.

CI never skips — `GITHUB_ACTIONS` disables the *skip*, not the memo, which is still written on green (which is precisely why a cached workspace could carry one back). `GATE_FORCE=1` forces a full run by hand.

`.streamlit/config.toml` — **an IBM Carbon theme and two server options.** Carbon v11 tokens over IBM Plex Sans/Mono vendored under `static/fonts/`, restored on 2026-09-22 after six weeks on the built-ins. Four choices are load-bearing, and the config header argues each:

- **`primaryColor` is Blue 60 `#0f62fe`, not a red.** Red is what the `negative` verdict wears, and the built-in themes' `#ff4b4b` primary put it **0°** away from the Run button, the active tab underline and every toggle — the verdict dressed as chrome. Blue 60 is 137.7° off, and white on it is 5.00:1 where the stock red was **3.30:1**, below AA for the Run label. This is the whole reason the theme exists; `_SENTIMENT_COLOR`'s comment points here.
- **Every sentiment hue is pinned as an explicit `<color>TextColor` in both modes.** Left unset, Streamlit *derives* the text variant from `<color>Color` — lightening on dark, darkening on light — which is what turned Carbon's Red 50 into a salmon `#fc979c` in the theme that shipped until 2026-08-14. Pinned, the metric renders the token itself (measured: `rgb(250,77,86)` = Red 50 dark, `rgb(66,190,101)` = Green 40). `TestThemeConfig` pins the presence, not the values.
- **`baseFontSize = 15`.** IBM Plex Sans at the 16 px root sets the five-tab results strip at **397 px** against a 404 px floor — a clip. At 15 it measures **372 px of 414**. It rescales every rem dimension with it, which is why the Layout figures below are 37.5 / 75 / 414 rather than 40 / 80 / 404; body text lands at 13.125 px, optically stock 14 px Source Sans by x-height. `metricValueFontSize = "2.4rem"` holds the verdict at 36 px against that root.
- **The fonts are self-hosted**, in `static/fonts/` — **six** woff2 files, **124 KB**, declared by `[[theme.fontFaces]]` and served because `server.enableStaticServing = true`. Six, not ten, because **Plex Sans is a variable font**: Google serves one byte-identical file for wght 400, 500 and 600, so three faces per subset were three copies of the same 40 KB fetched under three URLs that share no cache. One face per subset with `weight = "100 700"` renders **pixel-identically** (verified three times at 1000 px: 0 differing pixels) while fetching one file. A canvas `measureText` A/B in the same session also matched at 400/500/600, but that probe is only trustworthy when the same subsets are loaded in both runs — a re-measure before latin-ext has finished loading silently measures the fallback for any non-latin glyph in the test string, which is what makes the rendered-page diff the authoritative check; weight 700 now resolves to true bold instead of clamping to the 600 face, which nothing on screen currently uses. Plex Mono is *not* variable — its 400 and 600 are genuinely different files — so it keeps one face per weight. Only **latin and latin-ext** are vendored, narrower than the Google URL this replaced (which also served cyrillic, greek and vietnamese on demand): that covers the 12 output languages, Czech being the one needing latin-ext, but text *input* in those other scripts now falls back to Source Sans. So the app renders identically offline and **no font request leaves the machine**; verified against the Google-Fonts version of the same theme at 1000 px, where the two renders differ by **one pixel at delta 1/255**. Each face carries an explicit `unicodeRange`: without it the browser stops at the first matching face and never fetches latin-ext, which would drop Czech (`ě š č ř ž ů`, one of the 12 output languages) into the fallback face while the rest of the page stayed Plex. A face's *keys* matter as much as its values — Streamlit builds each one with `ParseDict` inside a bare `except Exception`, so a single mis-cased `Weight` raises, is logged as a warning and **drops that whole face**. `Source Sans` / `Source Code Pro` stay named in the stacks as the fallback. The favicon is vendored too (below), so **the app makes no third-party request at all**. Changing a `fontFaces` table needs a server restart, not a rerun; IBM Plex is SIL OFL 1.1 and `static/fonts/LICENSE.txt` travels with the files.

Two things are accepted rather than fixed. `primaryColor` is also the selected tab-label and selected-chip *text* color, and Blue 60 on `#161616` is **3.62:1** — above the 3.0 non-text floor, below AA for 13 px text; no single hex clears both white-on-primary ≥ 4.5 and primary-as-text ≥ 4.5 on a Gray 100 page, and Carbon itself ships Blue 60 on g100 for interactives. And under deuteranopia the three chromatic verdict hues converge, so the *word* is the value and color only reinforces it — which is why `render_result` never renders sentiment as a bare swatch.

The server option retires a console flood: with the watcher on, `streamlit run` logged about **109 `ModuleNotFoundError: No module named 'torch'` tracebacks after every Run**, at `WARNING`, from `LocalSourcesWatcher.get_module_paths` — the hot-reload watcher probes every `sys.modules` entry with `hasattr(m, "__path__")`, and transformers 5 pre-registers lazy placeholder modules whose `__getattr__` imports the real file on *any* attribute access, which for the vision image-processors means `import torch`. Streamlit caught each one and the app was unaffected, but a failed import never replaces the placeholder, so every rescan hit the same 109 (~0.4 s each) — and it rescans whenever `sys.modules` changed since the last scan, which the failed imports themselves guarantee by pulling in sibling modules before they raise (observed on both of two consecutive Runs). It predates the 2026-09-21 upgrade (105 on transformers 5.15.0, 109 on 5.17.0; the watcher is byte-identical between streamlit 1.61.1 and 1.64.0). `"none"` is the only knob that works — `AppSession` skips `register_file_watchers()` entirely on that value, whereas `poll`/`watchdog` only change how the paths the scan produces are watched, and a folder blacklist is applied after the scan. Verified live: two real Runs produced an 8-line log against 5,029 lines for the same sequence with the watcher on. The cost is the one the option names — no automatic rerun when a source file changes; press **R** or restart `streamlit run` — and `AppTest` is unaffected, since it never constructs a watcher.

**Theme faults are invisible at runtime** — Streamlit only ever *warns* on a theme problem, it never raises — so four of them are pinned by `TestThemeConfig` (see Tests), each verified to turn the suite red by mutating this file: a lone `[theme]` block with no per-mode sections beside it locks the app to one mode and drops the appearance toggle; a mis-cased key like `backgroundcolor` disables that style; a `[theme]`-only key (`baseFontSize`, `metricValue*`, `showSidebarBorder`) copied into `[theme.dark]` is ignored where it sits; and a dropped `<color>TextColor` silently restores the derivation. The first two guards were carried by the 2026-06 Carbon theme and lost when it was removed; the last two are new. One risk is independent of any theme: `_SENTIMENT_COLOR`'s four hues must be **built-in Streamlit color names**, since `:teal[…]` is not an error but literal punctuation on the page.

The theme was removed on 2026-08-14 and restored on 2026-09-22 by a judged design pass (five rendered candidates, three scoring lenses, three adversarial reviews; the record and the rejected directions live in the config header). What changed between the two Carbons: the workspace is Gray 100 rather than White/Gray 100 with a Carbon Black sidebar rail one step below it, every sentiment hue is pinned instead of derived, `baseFontSize` fits Plex under the strip ceiling instead of overrunning it by 1 px, and the sidebar, dataframe, code and link colors are set per mode instead of inheriting defaults tuned for a different background. The **two-key alternative** was measured and rejected rather than missed: `primaryColor` alone (`#1f6feb` dark / `#0068c9` light) on the built-ins fixes the collision, keeps the bundled font and the 377 px strip, and costs nothing in documentation — it is the fallback if the Google Fonts dependency or the rescaled rem figures ever stop being worth it.

### Environment

`load_dotenv()` runs at the top of `streamlit_app.py`, before `load_model()` contacts the Hugging Face Hub.

- `HF_TOKEN` — optional Hugging Face access token (read scope). The Granite model is public, so it is not required; without it the HF Hub logs an "unauthenticated requests" warning and applies lower rate limits / slower Xet downloads.
- **Local**: set `HF_TOKEN` in `.env` (gitignored; copy from the committed `.env.example`). Loaded automatically by `python-dotenv`.
- **Deploy**: set `HF_TOKEN` as a real environment variable / platform secret. `load_dotenv()` does not override existing env vars and no-ops when no `.env` is present, so the same code works in both environments without shipping `.env`.

- `MAX_INPUT_TOKENS` — optional integer input-token budget (default `16384`, clamped to `MODEL_MAX_TOKENS = 131072`). Resolved once at import by `_resolve_max_input_tokens()` (non-integer, zero, or negative → default, so a sign typo can't silently cap input to one token). Raising it increases context but also memory (~80 KB KV cache/token on the 3B) and prefill latency, so the default stays conservative and larger-RAM Macs opt into more. Set the same way as `HF_TOKEN` (`.env` locally / real env var on deploy).

## Architecture

`streamlit_app.py` — single-file app. Single-shot flow: one input → run the selected features → show results. An IBM Carbon light/dark theme (`.streamlit/config.toml`; see Configuration), native components, Material Symbol icons, a settings **sidebar** (the feature toggles and the output language — never the Run button; see Layout), `layout="wide"`.

**`layout="wide"` and the full-width results panel are load-bearing, not cosmetic.** The results panel carries five icon-prefixed tabs whose labels need **372 CSS px** together (measured on 1.64.0 under the shipped theme's 15 px root; 377 under Streamlit's bundled Source Sans at the 16 px default, and **397** under IBM Plex at that root — which is why `baseFontSize = 15` is load-bearing, see Configuration). Below that, `st.tabs` degrades *silently* into a horizontally scrolling strip with a chevron that hides whichever label is furthest from the active one — visible in the screenshot that shipped until 2026-08-15, where the `JSON` tab was scrolled out of frame. The panel's width has been re-argued three times, and the history is why the current answer is "no columns at all":

- Until 2026-08-15 the panel was half the page, so the room for the strip was a function of window width (`0.5 × viewport − 88`), clipping below roughly **930 px**; `layout="wide"` alone only moved that threshold.
- From 2026-08-15 a **2:3** split (`st.columns([2, 3])`) removed it structurally: even at 700 px the column was 393 px, and below ~640 px Streamlit stacks the columns anyway.
- On 2026-09-21 the settings moved into a **sidebar**, which re-opened it. The sidebar is 300 px wide by default (user-resizable, the width persisted in `localStorage`) and *pushes* the main area at viewports above 768 px rather than overlaying it, so a results column sharing what is left with any other column clips again — the design pass also considered an input | results split, and measured on 1.64.0 with the sidebar open a 2:3 split gives the results 316 px at a 1000 px window and 376 px at 1100 (one pixel short), while a 1:1 split is worse (262 / 312). Only a **full-width** panel clears the strip at every desktop width (a phone-width window under ~402 px, where the 15 px padding leaves less than 372, still clips — no Mac window is that narrow, and the column layout clipped there too): its narrowest case is **414 px at an 864 px window** — the smallest width at which wide mode still pads 75 px per side (the breakpoint is an inclusive `min-width: 864px` in **px** and did not move with the root; only the padding is rem-based, so it is 75 px rather than 80, and at ≤ 863 px it drops to 15 px) *and* the sidebar still pushes (at ≤ 768 px `initial_sidebar_state="auto"` collapses it entirely), so both neighbours are wider — 533 px at 863 falling to a second local minimum of **439 px at 769** (still 67 px clear), against 550 / 830 / 990 px at 1000 / 1280 / 1440. Re-measured under the theme on 2026-09-22: the margin at the floor *grew*, from 27 px to **42 px**. The cost, relative to that input | results alternative, is that the text and its analysis are not side by side on a wide display (they never were in the column layout either — the input was always a full-width block above the split); the judged design pass accepted that over a clip band a user would hit just by resizing a window.

A sidebar dragged wider than ~342 px at an 864 px window (or ~478 px at 1000) re-clips the strip — and because the width is remembered in `localStorage`, one drag leaves every later session clipped, a sticky state the column layout could not produce; the `initial_sidebar_state` integer width and `"locked"` could bound it but postdate the `>=1.57` floor (see Dependencies), so the trade-off is stated in the code comment and accepted. Removing an icon would also widen the margin and is the wrong fix: `TestUIPolish` pins `JSON_TAB_LABEL`'s icon and the `icon` + `tab_label` composition for every feature.

### Model

```python
from mlx_lm import generate, load

model, tokenizer = load("ibm-granite/granite-4.2-3b-bf16-mlx")
```

`load_model()` is called lazily inside the Run handler (not at module import), so importing the module — e.g. in tests — does not load the ~7.3 GB model.

**Granite 4.2 thinks by default, and the app turns that off explicitly.** The 4.2 chat template is ChatML (`<|im_start|>role\n…<|im_end|>`; 4.1's `<|start_of_role|>` markers are `<|unused_*|>` token ids in 4.2, so the two generations' prompts are mutually unreadable) and with `add_generation_prompt=True` it ends the prompt in `<|im_start|>assistant\n<think>\n` unless `enable_thinking=False`, which ends it in `<think></think>` instead. Two things make the kwarg mandatory rather than merely advisable, both verified against the installed stack on 2026-09-21 — first on mlx-lm 0.31.3 / transformers 5.15.0 / tokenizers 0.22.2, then again the same day on transformers 5.17.0 / tokenizers 0.23.2 with identical rendered prompts and token ids (the `tokenizer.json` load path that `TokenizersBackend` takes for this repo is byte-identical between the two; 5.16.0 is what admitted tokenizers 0.23, huggingface/transformers#46381, so the pair moves as a unit):

- **Omitting the kwarg is not "off".** mlx-lm's `TokenizerWrapper.apply_chat_template` injects `enable_thinking=self.has_thinking` when the caller passes nothing, and `has_thinking` is true for any tokenizer whose vocab holds `<think>` — 4.2's does (and so did 4.1's, unused). An explicit kwarg is honored; an absent one renders the thinking prompt. `TestRunFeature` pins the explicit `False`.
- **A thinking run is a silent JSON failure, not a slow success.** Measured: Sentiment on the Product review with the kwarg omitted spends its entire 128-token budget on `We need classify overall sentiment: positive, negative, neutral, mixed. The text: overall positive, with one minor gripe…` and parses to `None`. Had the budget been larger, `parse_json_output` — which returns the *first* object in the string — could instead have returned a draft object written inside the reasoning.

Two claims in the model card's own README did **not** survive verification, which is why `run_feature` still passes the rendered *string* to `generate()` and still builds its sampler with `make_sampler`: the card's "always pre-tokenize with `add_special_tokens=False`, or a spurious BOS collapses the thinking block" warning does not reproduce here — mlx-lm does re-encode a `str` prompt with `add_special_tokens=True` whenever the prompt does not already start with the BOS (`generate.py`; a ChatML prompt never does), but this tokenizer's post-processor adds no special tokens and `add_bos_token` is false, so the token ids are identical either way (checked via both `mlx_lm.utils.load_tokenizer` and `AutoTokenizer`, first id `<|im_start|>`, no `<s>`); and the card's Python examples pass `temp=`/`top_p=` straight to `generate()`, which raises `TypeError: generate_step() got an unexpected keyword argument 'temp'` on the very mlx-lm version IBM converted with. The model cards for all nine IBM MLX repos are one generated template; treat them as describing an intended loader, not this one.

### Constants

- `MODEL_NAME` — `ibm-granite/granite-4.2-3b-bf16-mlx`, **IBM's own** full-precision (bf16) MLX build of `ibm-granite/granite-4.2-3b`: ~7.3 GB of weights in two safetensors shards (no `model.safetensors.index.json` — `mlx_lm.load` globs `model*.safetensors`, so that is not an incomplete download), 3.66B parameters, `GraniteForCausalLM` with hidden 2560 / 40 layers / 40 heads / 8 KV heads / 131072 context. Not a community conversion: the `ibm-granite/…-mlx` repos are produced by IBM's release pipeline, and the `*-metadata.properties` file records `mlx_lm_version=0.31.3`, the version this project pins. Siblings `…-3b-q8-mlx` (~3.9 GB) and `…-3b-q4-mlx` (~2.1 GB, group size 64) are the small-Mac fallbacks; `…-8b-q4-mlx` (~5 GB) is the larger model at about the same footprint, with `…-8b-q8-mlx` (~9.3 GB) and `…-8b-bf16-mlx` (~17.6 GB) above it. `mlx-community` publishes no 4.2 conversions. Quantization touches weights only, so the ~80 KB/token KV cache (40 layers × 8 KV heads × 64 head dim × K+V × bf16) is the same across the 3B variants — half the 8B's 160 KB. The README carries the machine-side envelope (~16 GB unified memory). The model card's "bf16 needs ≥16 GB / q4 fits 8 GB" table is verbatim boilerplate across all nine IBM MLX repos and is only arithmetically true for the 3B.
- `MODEL_MAX_TOKENS = 131072` — Granite 4.2's 128K context ceiling (`max_position_embeddings`, unchanged from 4.1); configured caps are clamped to it.
- `MAX_INPUT_TOKENS` — input-token budget; inputs longer than this are truncated (with a warning) before analysis. Defaults to `16384`, overridable via the `MAX_INPUT_TOKENS` env var (see Environment), resolved by `_resolve_max_input_tokens()`.
- `TEMP = 0.0`, `REPETITION_PENALTY = 1.2` — fixed decoding params. `temp=0.0` is greedy/deterministic (`make_sampler` returns argmax), which keeps the JSON-emitting features reliably parseable and the README screenshot reproducible; `top_p` is left at its default since it has no effect under greedy decoding. **This is a deliberate deviation from IBM's guidance**, not an oversight: the Granite 4.2 card marks `temperature=1.0` "Required for all modes" and says to use `top_p=0.95` alongside it "across all tasks and serving backends", and ships both in `generation_config.json` (which mlx-lm ignores except for `eos_token_id`). Measured on 2026-09-21 under the shipped prompts across the three samples × English/German/Japanese × three JSON features, greedy and `1.0/0.95` both parsed **81/81** (three draws per sampled case), so sampling buys no parse-rate and costs determinism. Re-run that A/B if the JSON prompts or the model change again. The repetition penalty is applied to **prose only** (it would fight the repeated structural tokens JSON requires).
- `FEATURES` — `list[dict]` registry; each entry has `key`, `label` (toggle), `tab_label` (result tab), `icon` (the result tab's Material Symbol shortcode, e.g. `:material/mood:`), `help` (toggle tooltip), `output` (`"prose"` or `"json"`), `max_tokens`, `system`, and `user_template` (formatted with `{text}`). JSON entries additionally carry `localized_field` — the phrase naming that feature's own free-text value (`"every topic label"`, `"the rationale text"`) that `language_directive` drops into the prompt. It lives in the registry rather than as a branch inside `language_directive` so a new feature can't inherit another's field name; `language_directive` indexes it directly, so omitting it raises a `KeyError` instead of instructing the model to translate a field the schema lacks. `TestFeatures` also checks the phrase names a field the feature's own schema declares.
- `LABELS` — `{key: label}` derived from `FEATURES`.
- `JSON_TAB_LABEL` — `":material/data_object: JSON"`, the combined-output tab's label. One definition on purpose: the UI suite imports it to locate the results panel (`_results_panel`) and to pin the icon (`TestUIPolish`), so a rename cannot leave the two disagreeing.
- `SAMPLE_TEXTS` — `{name: text}` built-in samples for the Sample tab.
- `LANGUAGES` — the **Output language** selectbox list (13 entries): the `LANGUAGE_AUTO = "Match input"` sentinel (the default, not itself a language), followed by Granite 4.2's 12 officially tested output languages (unchanged from 4.1) — the first of which is `LANGUAGE_ENGLISH = "English"`. Input is multilingual regardless; this controls output language.
- `_LOCALIZED_TOKEN_MULTIPLIER = 2` — every **non-English** output language (including "Match input") gets `max_tokens × 2` via `_effective_max_tokens`, since localized output costs more tokens than the English-tuned budgets and a JSON feature that overruns truncates mid-object and fails to parse. `max_tokens` is a ceiling, so the headroom is free for short output. This deliberately covers Latin-script languages, not just CJK/Arabic — a `_TOKEN_HEAVY_LANGUAGES` set previously narrowed it to Japanese/Chinese/Korean/Arabic, which held only while the rationale field was (incorrectly) staying English; once `language_directive` was fixed, a localized German rationale overran Sentiment's 128-token budget.

The four features: Summarization (prose, 256 tokens), Topic detection and Intent recognition (JSON, 256 tokens), Sentiment (JSON, 128 tokens). The three JSON features share **`_JSON_SYSTEM`**, one module-level template each formats with its own schema — IBM's "answer in JSON … `<schema>`" pattern reproduced verbatim, trailing newline included. Output is not guaranteed JSON, so it is parsed defensively.

> **Design decision (2026-08-12):** `language_directive`'s JSON wording was settled by an A/B of five phrasings against the live model (greedy decoding, so single runs are deterministic), scored on Japanese topic labels and rationale localization. Two independent variables emerged. **Clause order** decides whether `rationale` localizes at all: both candidates ending on the keep-English clause left it in English; all three ending on the localize clause localized it. **Quoting the field name** wrecks topic labels: `each topic "label"` collapsed them into meaningless katakana (`メーマイファーション`), while the otherwise-identical unquoted `every topic label` produced clean output — the quotes appear to read as a literal string to emit rather than a field to translate. Shipped: exception first, requirement last, field named unquoted. A knock-on: once the rationale actually localized, a German one overran Sentiment's budget and truncated mid-object — see `_LOCALIZED_TOKEN_MULTIPLIER`. Don't "simplify" this wording without re-running the A/B.
>
> A follow-up A/B (same day) tried to remove what looks like dead weight: all three JSON features are told to "keep enumerated values (such as the sentiment label) in English", but only Sentiment has an enum, and in the Topics prompt the word *label* collides with the field being localized. **Both** feature-aware replacements — a keys-only clause where no enum exists, in two phrasings — collapsed Japanese topic labels into meaningless katakana (`モーロウングイス`, `ビルグイングイン`) while leaving German *better*. The clause is load-bearing for non-obvious reasons and was kept verbatim on all three features. Note the automated scorer passed all three candidates: its "is it localized?" check was a CJK codepoint test, and degenerate katakana is still CJK. Any future A/B here needs a meaningfulness check, not just a script check.

> **Design decision (2026-06-05):** Granite's native tool-calling (`tools=` → `<tool_call>` blocks) was evaluated as an alternative structured-output channel for the classification features and **rejected**. An A/B over a 55-case adversarial corpus showed no benefit — schema-valid **53/53 tied**, accuracy **45 vs 44** (noise), diverging only on prompt-injection where tool-calling was marginally *worse*. The uniform JSON-prompt approach was kept; don't re-litigate without a material model/task change. **Caveat (2026-08-12):** those are **bf16-era figures**, the baseline a re-run would compare against — they have not been re-measured on the 4-bit default now shipped. The 4-bit evidence is weaker: 12/12 parses across the built-in samples plus 12 more across Japanese/German/"Match input", which is not the adversarial corpus. Re-run the corpus before citing 53/53 as evidence about the shipped model. **Caveat (2026-09-21):** the swap to Granite 4.2 is the material model change this decision was hedged against, and it also changed the tool channel itself — 4.2 emits Qwen3-Coder-style XML (`<function=…><parameter=…>`, parser `qwen3_coder`) rather than 4.1's JSON `<tool_call>` — so the 4.1 A/B says nothing about 4.2 tool-calling. The JSON-prompt path was **re-verified** on 4.2 under the shipped prompts (36/36 parses across the built-in samples × four languages, plus 81/81 in the decoding A/B) and kept on that basis. Whether tool-calling would now do *better* is unmeasured; measure before claiming either way.

> **Design decision (2026-09-21):** the move from `mlx-community/granite-4.1-8b-4bit` to `ibm-granite/granite-4.2-3b-bf16-mlx` re-opened the `language_directive` A/B, exactly as the 2026-08-12 note warned. Under the 4.1 wording, 4.2-3b localized only **11 of 21** JSON fields (three samples × German/Japanese × three features, plus a German-input "Match input" case) — every Japanese `rationale` stayed English. It took three rounds, and the second one shipped a defect the review caught, so the sequence is worth keeping. **Round 1** (seven wordings, greedy, script check plus a read of every output): placement matters — the same clause moved into the system prompt scored 9/21 and a short "Respond in <language>." prefix ahead of the suffix 17/21, so the suffix stays; requirement-first-only scored 10/21, so the 4.1 finding that the prompt must *end* on the localize clause still holds; and two ideas each scored 20/21 — restating the requirement at both ends (`C`) and appending "entirely in <language>, every sentence of it" to the 4.1 wording (`D`). **Round 2** (hybrids): combining them scored 21/21 by script and was rejected on the read — its extra hits were garbled German compounds (`Batteriezahnlänge`, `Paarungsbeschleunigung`, `Schallschneide`), localized-but-meaningless, the failure the 2026-08-12 note said the script check cannot see; `D` was shipped as the smallest change. **The review then found `D` echoing**: under `LANGUAGE_AUTO` the target reads "the same language as the text above", and "…, every sentence of it" binds *it* to the text above, so the model copied the input verbatim as its `rationale` — for the German-input case *and* for the built-in Product review, i.e. the app's default path. The round-1 corpus had no English-sample "Match input" cases and no echo check, so nothing could have seen it. **Round 3** added both (three samples under "Match input", a German and a Japanese input under "Match input", and an echo detector: normalized rationale contained in the normalized input, or `SequenceMatcher` ratio ≥ 0.75): `D` echoed 3 of 15 default-path rationales; every variant keeping "every sentence" echoed at least once; and the both-ends form with a short "entirely" closer (`K`) localized **9/9 German, 9/9 Japanese, 9/9 English-input and 3/3 German-input "Match input"** with **zero echoes** and fluent rationales throughout. Shipped: `K` — `Write <field> in <language>. <keep-English clause>. Write <field> entirely in <language>.` Its known blemish is one garbled label (`Batteriezahle`) in the Product review's German topic set, the set the 4.1 wording left in English and the round-2 winner turned into three garbled compounds. One limitation is shared by every wording tried and is the model's, not the prompt's: with **Japanese input** under "Match input", 4.2-3b answers in English (0/3 in every round) — an explicit "Japanese" selection localizes 9/9. The `language_directive` docstring and `TestLanguageDirective` carry the same account, including a negative assertion that keeps "every sentence" out.

### Session State

`st.session_state.results` — `dict | None`. Set on Run to `{"order": list[str], "data": {key: {"raw": str, "parsed": dict | None}}, "truncated": bool, "signature": (input_text, toggles, language)}`; `None` before the first run. Persists across reruns; the `signature` lets the results panel flag when the live input/toggles/language differ from the run. Both the stored and live signatures are built by `_run_signature(input_text, enabled, language)` so the two sides can't drift.

### Layout

A settings **sidebar** beside a main area that stacks, top to bottom: the title, the full-width input section, the **Run row**, and the full-width results panel. Nothing uses `st.columns` any more, so nothing stacks or reflows at Streamlit's 640 px column breakpoint; the one responsive behaviour is the sidebar's own (`initial_sidebar_state` at its `"auto"` default: expanded on desktop, collapsed at or below 768 px, and on 1.64 a manual collapse persists in `localStorage`).

- **Sidebar** — run *settings* and one line of metadata, in the sense of Streamlit's own layout guidance (global filters, settings and small app metadata go in; content and results stay out) — and, by this project's own rule rather than Streamlit's, never the primary action: a "Features" subheader over the four `st.toggle` widgets (default on; each description in its `help=` tooltip), the **Output language** selectbox (`LANGUAGES`, default "Match input" — it applies to every feature, and the sidebar's own width is the constraint the old `st.columns([1, 2])` existed to provide), and a caption naming the model (short name; the full id wraps to three lines at the default 300 px) and the `MAX_INPUT_TOKENS` cap the truncation warning refers to. **Run is deliberately not here**, and `TestSidebarLayout` pins that: the sidebar collapses, the collapse is remembered, and the app's one trigger must never sit behind a chevron. In the sidebar's vertical container the toggle labels wrap normally and carry no native `title` tooltip (verified in the DOM on 1.64.0: `title=""`, `white-space: normal`), so the since-1.63 no-wrap rule for direct column children no longer touches them.
- **Input** — `st.tabs(["Text", "Upload", "Sample"])` (each label prefixed with a Material Symbol icon), full width; the active input is resolved by precedence **Text > Upload > Sample** (first non-empty). The uploader accepts `.txt` and `.md` only (`type=["txt", "md"]`) and decodes with `errors="replace"`, so undecodable bytes become U+FFFD rather than raising — a strict decode turns a latin-1 `.txt` into a `UnicodeDecodeError` traceback where the Run row and results panel should be (`TestRunInteraction` pins the decode, the preview and the precedence at the call site). The Upload and Sample tabs each preview their text through the shared `_preview` helper — **not** a `disabled=True` `st.text_area`, which is what shipped until 2026-08-15: Streamlit renders a disabled textarea at `fadedText40` (forced through `-webkit-text-fill-color`, so it cannot be overridden), which reads as a broken input rather than a read-only preview. It is **not** a tab-order problem — a `disabled` control, unlike `readOnly`, is removed from sequential focus navigation, and an earlier version of this note claimed the opposite. The real trade-off is the accessible name: the textarea carried a collapsed label and a bare container has none, and Streamlit exposes no label on a container.
- **Run row** — directly under the input, a `st.container(horizontal=True, vertical_alignment="center")` holding the **Run** button at its natural width (a `:material/play_arrow:` icon, `type="primary"`, 70 px measured under the theme's 15 px root, 73 px at the 16 px default — stretched across a full-width main area it would be an eyesore; disabled until there is input and at least one feature is on) and **exactly one** `st.caption` beside it: why Run is disabled ("Paste text, upload a file or pick a sample to enable Run." / "Turn on at least one feature in the sidebar to enable Run.") or, once enabled, a mirror of the settings the sidebar may be hiding (`"N of 4 features · Output language: <language>"`). A greyed-out button says nothing about why, and with the settings in a collapsible sidebar the caption is the one place the main area states what a click would do. The disabled reason (`blocker`) is computed once and drives both `disabled=` and the caption — a condition added to one cannot be missing from the other, which a first version with two separate encodings did not guarantee — and a single `st.caption` call is what keeps the row at exactly `[button, caption]`. One caption on every path keeps the row's shape fixed at `[button, caption]` — the explanation always sits beside the control it explains — which `TestRunRow` pins along with the container's horizontal direction. The row is 37.5 px tall (measured); of the three captions only the no-feature one still wraps under the button, and only in an **864–868 px window** — it needs 420 px of content against the 414 px floor, while the no-input and enabled captions clear the floor at every width the sidebar stays open. (Re-measured on 2026-09-22; under the bundled font at the 16 px root the no-feature caption needed 428 px and the no-input one 420, against a 404 px floor, so both of those could wrap.) Since Streamlit 1.63 (streamlit/streamlit#16578) a widget placed *directly* in a column or a horizontal container resolves its default `wrap=None` to no-wrap, so the button carries a native `title="Run"` tooltip (verified in the DOM on 1.64.0) — now the only control that rule touches. The tooltip is Streamlit's, not app code; `wrap=True` would restore wrapping but is a 1.62+ kwarg and would have to join the floor list above.
- **Results panel** — a wrapper `st.container()` holding, in order, a reserved `st.container()` (run status), a reserved `st.empty()` (the notices; the *empty* is load-bearing, see Performance) and the fixed result tabs, **all emitted before the Run handler executes**: `JSON` plus one tab per feature, derived from `FEATURES` (each feature label composed as `icon` + `tab_label`; the `JSON` tab carries an icon too). JSON shows the combined output; each feature tab renders its result (guarded by try/except), a "not enabled for this run" note if it was off, or a run prompt before the first run ("Choose features in the sidebar and click Run to see results here." — `TestInitialRender` asserts both the `in the sidebar` and the `click Run` substrings). An "Inputs changed since this run — click Run to refresh." note appears when the live input/toggles/language differ from the run, and since the notices slot sits directly under the Run row it lands next to the button it names. Rendered from `st.session_state.results`. The wrapper makes the panel one addressable block — one `with`, one node whose children `TestResultsPanelStructure` pins as exactly `[status, notices, tabs]` — and nothing more: it does **not** protect against something emitted above it, since the wrapper itself sits at the fourth top-level index of the main area (after the title, the input tabs and the Run row, all unconditional) and an element inserted above it at top level moves the wrapper and remounts everything inside — the same remount the slots would suffer without a wrapper. That is why `TestResultsPanelStructure` also pins the top-level shape `[title, tab_container, flex_container, flex_container]` and that the panel *is* `at.main.children[3]`; the Run row's contents cannot move it (they live under the row's own path), which is why that row's caption count is a row-shape concern, not a panel-index one.

Interactive widgets carry stable `key=`s so `AppTest` can address them by key rather than positional index: `paste` (text area), `upload` (file uploader), `sample_select` (sample segmented control), `feature_<key>` (per-feature toggles, e.g. `feature_summary`), `language` (output-language selectbox), and `run` (the Run button).

### Functions

- `load_model() -> tuple[nn.Module, TokenizerWrapper]` — loads model and tokenizer via `mlx_lm.load`, cached with `@st.cache_resource`.
- `truncate_to_tokens(text, tokenizer, max_tokens=MAX_INPUT_TOKENS) -> tuple[str, bool]` — truncates to a token budget; returns `(text, was_truncated)`.
- `parse_json_output(raw) -> dict | None` — returns the first JSON **object** found anywhere in the string (tolerates surrounding prose/code fences via `JSONDecoder.raw_decode`) — **including the first object nested inside a top-level array**, since the whole-string fast path returns only on a `dict` and everything else falls through to a scan for `{`. Only input containing no parseable object (scalars, arrays of scalars, unparseable text) returns `None`.
- `resolve_input(pasted, uploaded, sample) -> str` — resolves the active input by precedence (pasted > uploaded > sample); each candidate is stripped first, so a whitespace-only entry falls through.
- `language_directive(feature, language) -> str` — clause appended to the **user** turn telling the model which language to answer in. Localizes only free-text *values* (summary prose, rationale, topic labels); JSON keys and enums (e.g. the sentiment label) stay English so `parse_json_output` / `render_result` keep working. Returns `""` for `"English"`; `"Match input"` mirrors the analyzed text's language. Four wording choices are load-bearing and were each settled by an A/B against the live model (see the design decisions below): the keep-English exception comes **first** and the localize requirement **last**; the JSON branch names the feature's own field (rationale / topic label) rather than "all free-text field values"; that field name is **unquoted**; and the requirement is stated at **both ends** — a plain "Write <field> in <language>." opener and a "Write <field> entirely in <language>." closer — the strengthening 4.2-3b needed, with "every sentence of it" deliberately absent (it makes the model echo the input under "Match input"). The prose branch also forbids notes about the language used, which otherwise leak in as a trailing English aside.
- `_effective_max_tokens(feature, language) -> int` — the feature's `max_tokens`, doubled for every non-English language (see `_LOCALIZED_TOKEN_MULTIPLIER`); the base budget for English.
- `_strip_control_markers(text, tokenizer) -> str` — drops every string in `tokenizer.get_added_vocab()` from untrusted input before it is formatted into the prompt. The tokenizer turns the literal text of any *added* token back into its control id wherever it appears, so a pasted ChatML transcript (`<|im_end|>\n<|im_start|>assistant\n<think></think>…`) would end the user turn and open an assistant turn of its own — verified against the 4.2 tokenizer, and far likelier with ChatML markers than with 4.1's `<|start_of_role|>`. The set is the *added* vocabulary, not `all_special_tokens`: on Granite 4.2 only `<s>`, `<unk>` and `<|im_end|>` are special, and `<|im_start|>` — the marker that opens an injected turn — is not. Markers are removed, not escaped, since they are control syntax the tokenizer offers no escape for; ordinary angle brackets and pipes survive.
- `run_feature(feature, text, model, tokenizer, language=LANGUAGE_AUTO) -> dict` — strips control markers from `text` (above), then builds `[{"role": "system", …}, {"role": "user", …}]` (system prompt verbatim; the user turn carries the `language_directive`), renders it with `tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True, enable_thinking=False)` — the last kwarg is mandatory and explicit, see Model — and passes that string to `mlx_lm.generate` with `_effective_max_tokens(feature, language)`, `make_sampler(temp=TEMP)`, and — **for prose only** — a `make_logits_processors` repetition penalty (`logits_processors=None` for JSON). Thinking is off, so `raw` carries no `<think>` block to strip. Returns `{"raw": str, "parsed": dict | None}` (`parsed` only for JSON features).
- `_run_signature(input_text, enabled, language) -> tuple` — the run's identity `(input_text, toggle states, language)`; built on Run and recomputed live so the results panel can flag stale results. Single source so build/compare sides can't diverge.
- `_preview(text) -> None` — renders read-only source text in a fixed-height `st.container(height=150)` holding `st.text(…, width="stretch")`; `st.text` is proportional, not monospace, and cannot exceed its parent's width, so long prose wraps inside the scrolling container. Shared by the Upload and Sample tabs so the rationale (above) lives in one place rather than as a comment pointing at another comment.
- `_topic_rows(topics) -> list[dict]` — normalizes the model's `topics` value into rows `st.dataframe` can render. A non-empty-list check was not enough; all three survivors were reproduced against the installed Streamlit (1.61.1, and again on 1.64.0 on 2026-09-21 — same `value` column, same empty bar, and the mixed-list error is now `StreamlitDataframeConversionError`, a `StreamlitAPIException` subclass from 1.62.0's exception consolidation, so the caller's `except Exception` degrades it exactly as before). A list of **bare label strings** (`["politics", "economy"]`) converts to a single column literally headed `value` — `column_config` names nothing in it, so the labels lose their header and the confidence bar vanishes. A list *mixing* objects with scalars raises `StreamlitAPIException`, which `render_result`'s caller degrades to "Could not render this result." plus a traceback. And a list of objects carrying **no usable `label`** (`[{}]`, or `[{"confidence": 0.9}]` from a truncated object) renders a table of blank rows instead of falling through to "No topics found." Bare strings are promoted to `{"label": …}`, and an entry survives only if it has something to show in the Topic column — **both shapes are held to the same test**, which is what lets the caller's `if rows:` mean "there is a topic to render". Dropping is not data loss for the user because the JSON tab always shows the raw response. A promoted row has no `confidence`, which renders as an empty bar rather than raising.
- `_escape_markdown(text) -> str` — backslash-escapes every ASCII punctuation character (`string.punctuation`, which is exactly the set CommonMark lets a backslash escape), so a Markdown-parsing element shows `text` as typed. It exists for model strings that must sit in an element with no plain-text mode — an `st.metric` value, an `st.caption` — and is not used where `st.text` fits. Escaping *all* punctuation rather than a hand-picked list is load-bearing for one construct: the frontend rewrites `:material/` to `:material_` in the raw source before parsing, so a list that escapes `:` but not `/` (the review's first candidate) still rendered `:material/warning:` as an icon. Verified in headless Chrome on 1.64.0: escaped `$5 and $10`, `![x](https://…)`, `:red[x]`, `:material/warning:`, `:tada:`, `__init__`, `**b**` and `&copy;` all render as typed, and no image is fetched. What survives is what the frontend rewrites in the parsed *text*, after escapes are resolved — GFM autolinks (a bare URL, a `www.` host or an email address becomes a clickable link), the `:streamlit:` logo and `:material_<name>:` icons (both bundled), and `->`/`>=`/`--` typography. None of them makes a request.
- `render_result(key, result) -> None` — renders one feature's result with native components: the summary as `st.text`; a dataframe for topics (confidence as a `ProgressColumn`); `st.metric` for intent/sentiment, each with an optional rationale (`st.text`) and a percent-formatted confidence (`_render_confidence`). The sentiment value is color-coded by enum (`_SENTIMENT_COLOR` → `:color[…]` markdown, which resolves Streamlit's **built-in color names** against the active theme — positive→green, negative→red, neutral→gray, mixed→orange; an unrecognized name is not an error, it renders as literal punctuation, which is what `TestThemeConfig` pins), matched **case-insensitively** (`.lower()`, so `"Positive"` still colors); an out-of-enum label renders uncolored. Untrusted model output is guarded — `topics` is normalized by `_topic_rows` (an empty result falls back to a caption), `st.metric` values are coerced to strings, and JSON parse failures show the raw response via `st.code(raw, language=None, wrap_lines=True)`: the default `language="python"` would syntax-highlight model prose as code, and claiming `"json"` would be a guess on the one branch that runs *because* the output did not parse. Its **text** is untrusted too, and never reaches Markdown as-is. Until 2026-09-22 the summary and rationales went through `st.write`, which for a string *is* `st.markdown`, and the frontend runs remark-math with single-dollar math on: any two dollar amounts in one paragraph ("paid $120 … billed $120 again") lost both `$` signs to an inline-math span, localized forms ("120 $ … 120 $") included, and one KaTeX-eligible span anywhere turned the whole paragraph into math italics. An image in the output — echoed from pasted or uploaded input, which the 2026-09-21 echo finding shows this model does — rendered as an `<img>` the browser fetched, a tracking pixel from a local app; `:red[…]`, `:material/…:`, emoji shortcodes and `__init__` were rewritten too. The summary prompt asks for plain prose, so Markdown bought nothing: free text now goes to `st.text(…, width="stretch")`, which does no parsing and is the same proportional, wrapping call `_preview` uses. The model strings that still sit in a Markdown element — the intent and an out-of-enum sentiment in `st.metric` (always Markdown, no switch), and a non-numeric confidence in `st.caption` — go through `_escape_markdown`; the `:color[…]` wrapper is only ever built around one of the four allow-listed enum words. AppTest never runs the frontend that does the parsing, so `TestRenderResult` pins the call sites rather than the rendering.

### Performance

The load-bearing choices are stated where they are defined — lazy `@st.cache_resource` model load (Model), the `MAX_INPUT_TOKENS` truncation budget and greedy decoding (Constants). Two decisions have no other home:

- **The results panel's chrome is emitted before the run, not after** — a status `st.container()`, a notices `st.empty()`, then `st.tabs`; the `if run:` block fills them afterwards. Streamlit emits a delta per `st.*` call and leaves the *previous* run's elements on screen — faded to ~33% once a run outruns a short delay — until the new run re-emits them, and it only drops what was not re-emitted in `clearStaleNodes` at **end of run**. Two things follow, and only the second is what most descriptions of this pattern claim:
  - **The tab block now sits at a fixed child index.** It used to follow the two *conditional* notices, so its delta path shifted between 0, 1 and 2 as they appeared and disappeared; landing on a path previously held by a different node remounts the block and silently resets the user's selected tab. This is the bug the ordering actually fixes, and it is unrelated to how long inference takes.
  - **The tab bar paints immediately** instead of waiting out a 7.3 GB model load plus up to four generations. The tab *bodies* cannot — the results do not exist yet — so the previous run's answers are still what is on screen during a run. That is inherent, not a defect.
  - **The notices slot must be `st.empty()`, not a container.** Re-emitting an empty *container* preserves its existing children (they are only dropped at end of run), so a plain container would keep showing the previous run's "Inputs changed since this run" note, faded but readable, throughout a run it no longer describes. `st.empty()` clears at the top of the rerun; `notice_slot.container()` is what lets the one slot hold both notices. An earlier version of this section claimed the container reordering alone retired that note — it does not.
  - **The spinners repaint none of it**: `st.spinner` enqueues on a *transient* cursor (`get_transient_cursor` advances `_transient_index`, never `_index`), so it never touches the real delta path.
  - **`slot.skeleton()` is the wrong reservation**, despite being what Streamlit's own performance guidance reaches for: `SkeletonPlaceholder.__init__` calls `_enqueue`, which locks and advances the cursor, so the skeleton permanently consumes child index 0 — reintroducing exactly the shifting-index remount above.
  - Cost: an empty `st.container()` renders no DOM node at all and the `st.empty()` renders at height 0, so the reservation costs **one 15 px flex gap** above the tab strip (measured; it is `1rem`, so 16 px before the theme's 15 px root), not the stacked dead space it looks like it should.

  `TestResultsPanelStructure` pins the order by asserting the results panel wrapper's children are `[flex_container, empty, tab_container]` in `AppTest`'s block tree — apart from `TestRunRow`'s `[button, caption]` row-shape check, the rest of the UI suite asserts with `any(...)` over each collection and a set comparison for `at.tabs`, so nothing else here can see order.
- No `@st.fragment`: the one expensive op (inference) is already gated behind Run and `@st.cache_resource`-cached, so isolating reruns would add complexity for no gain — and a results-panel fragment would not even see the input/toggle/language widgets it depends on (they live outside it), breaking the cross-widget staleness note. `st.session_state.results` is initialized with `st.session_state.setdefault`.

### Error Handling

Unexpected exceptions during a run — and during per-feature rendering — are shown with `st.exception()`. JSON parse failures degrade gracefully to the raw response, and `render_result` guards/coerces untrusted model output before passing it to `st.metric` / `st.dataframe`, and never hands its text to Markdown unescaped (see Functions).

**A failed run clears `st.session_state.results`.** The run guard sets it to `None` before showing the traceback, because the tabs are already painted by then (see Performance): leaving the previous run's answers in place would show them *underneath* the traceback with nothing marking them stale, and the "Inputs changed since this run" note does not cover it — that note reads as "you edited something", not "this run failed". The cost is losing a good previous result to a transient failure, which is the cheaper of the two, since re-running is one click and a wrong-but-confident panel is not recoverable by the reader. `TestRunFailures` pins it, along with the parse-failure display.

Both of those `except Exception` handlers carry an inline `# noqa: BLE001` naming their role (top-level run guard / untrusted model output shape). `BLE001` ("do not catch blind exception") entered ruff's **default** rule set in 0.16, and it is right about blind catches in general — but these two are deliberate UI boundaries: a Streamlit script has no frame above it to catch anything, so an escaped exception blanks the page instead of showing the user what broke. The suppression is per-line rather than a project-wide `ignore` in `pyproject.toml` **on purpose** — the rule stays live, so a third, *unintentional* blind catch added later still fails the lint gate.

## Tests

`tests/test_streamlit_app.py` — unit tests (mocked, no model download). Data-driven cases use `@pytest.mark.parametrize` (each `pytest.param` carries an `id=` so failures are self-labeling); `TestRunFeature` shares a `tokenizer` fixture:

The suites that assert by *executing* a shell script (`TestReleaseWorkflow`, `TestHooksConfig`) share a **session-scoped `stub_bin` fixture**, and that is a performance contract, not tidiness. macOS scans every newly created executable the first time it runs — measured here at **241 ms**, against **4 ms** to re-run one already scanned *or to run it through a fresh symlink* (the scan is keyed to the inode, so a symlink into a fresh directory is free). Writing throwaway `gh`/`uv` stubs per test therefore cost ~17 s of a 21 s gate, paid again on every Stop hook, with essentially none of it spent on the tests' own logic. So the stubs are written once and varied through `$STUB_*` **environment variables** rather than by regenerating their source, and `release.sh` / `gate.sh` are **symlinked** into the throwaway repo instead of copied (both locate their root from the *working directory* via `git rev-parse --show-toplevel`, so a symlink resolves the same tmp repo a copy did). Tests still get a private bin directory with only the tools that case wants symlinked in, which is what keeps `omit=` honest — a tool left out stays genuinely unreachable rather than merely unstubbed. Net: pytest 19.7 s → 4.8 s, with mutation coverage re-verified unchanged. If a future stub needs per-test *behavior*, add an environment variable — do not go back to writing a file per test.
