# CLAUDE.md

**Granite Text Intelligence** — a Streamlit application for **summarization, topic, intent, and sentiment analysis** using IBM's [granite-4.1-8b](https://huggingface.co/ibm-granite/granite-4.1-8b) (instruct) on Apple Silicon with MLX (`mlx-lm`). A single-shot playground: you provide text (paste, file upload, or a built-in sample), toggle which analyses to run, and get the results back. All four features are powered by prompting a single Granite model; the three classification features request JSON and are parsed defensively. Output can be localized to any of Granite's 12 supported languages (default: match the input).

## Rules

Each is justified in the section named. The reasons are non-obvious and were paid for in failures — read the justification before deciding an exception is safe.

- **Never hand-edit `uv.lock`** — regenerate it with `uv lock`; the hook blocks edits to it. → *Commands*
- **Bump `version` and run `uv lock`, then land *both* files.** A lone `pyproject.toml` bump fails CI at `uv sync --locked`, and no release is cut. → *Commands*
- **After a `uv lock --upgrade` that moves `mlx`, `mlx-lm`, `transformers` or `huggingface-hub`, run the smoke test by hand.** No test executes a line of `mlx`. → *Verifying a dependency upgrade*
- **Treat a ruff/ty major as its own reviewable change**, not incidental lockfile noise — a linter upgrade can redefine the gate with no code change. → *Commands*
- **Don't reword `language_directive` without re-running the A/B.** Clause order and the unquoted field name are load-bearing. → *Design decision (2026-08-12)*
- **Any future prompt A/B needs a meaningfulness check, not just a script check** — degenerate katakana still passes a CJK-codepoint test. → *Design decision (2026-08-12)*
- **Don't re-litigate tool-calling** without a material model/task change. → *Design decision (2026-06-05)*
- **A new test stub gets a new `$STUB_*` env var**, never a file written per test — that cost ~17 s of a 21 s gate. → *Tests*
- **Use Conventional Commits.** `release.sh --generate-notes` turns subject lines into public release notes. → *Commits*
- **No `[theme]` section may ship.** The app uses Streamlit's built-in light and dark themes, and the gate rejects *any* custom theme — a correct two-mode one included. → *Configuration*

## Commands

- **Lint**: `uv run ruff check .`
- **Format**: `uv run ruff format .` — reaches **Markdown as well as Python**: ruff ≥ 0.16 formats the code inside `python`-tagged fenced blocks, so a mis-spaced snippet in `CLAUDE.md` fails `--check` in CI exactly like a `.py` file would. **Formatting only** — `ruff check` skips Markdown outright (it reports "No Python files found" and exits 0), so an unused or unsorted import inside a fence is *not* linted. `README.md` is untouched today; its fences are all `bash`.
- **Typecheck**: `uv run ty check`
- **Test**: `uv run pytest`

All four live in **`scripts/gate.sh`**, which CI (`.github/workflows/ci.yml`) and the Claude Code Stop hook (`.claude/settings.json`) both invoke, so the two cannot drift. It runs the *verifying* variants (`ruff format --check .`, `pytest -q`), so it reports formatting drift rather than fixing it. Reproduce CI with **`GATE_FORCE=1 ./scripts/gate.sh`** — a bare `./scripts/gate.sh` skips a tree that already passed (see the memo below), which reproduces the Stop hook but not CI. Run the individual commands above while iterating on one gate.

**Releasing** is a side effect of merging, not a command: bump `version` in `pyproject.toml`, run **`uv lock`**, and land **both files** on `main`. Once the gate is green CI runs `scripts/release.sh`, which tags `v<version>` and publishes a release with generated notes; every other push is a no-op.

`uv.lock` records the *project's own* version, so the two files move together. This is easy to half-do and the failure is quiet: a commit carrying only `pyproject.toml` fails CI at `uv sync --locked`, and since `release` needs `check`, no release is cut — it looks like the automation stopped working. Nothing local catches it, and the reason is worth knowing: every gate command runs under `uv run`, which **silently re-locks** before the command starts, so the working tree always looks consistent no matter what is staged (verified — a bump to `0.2.0` had rewritten `uv.lock` before pytest imported, and reverting `pyproject.toml` rewrote it back; one such relock also quietly dropped an `mlx-metal` platform marker). Running `uv lock` explicitly makes the update deliberate and visible before you stage rather than a side effect you might not commit. `uv.lock` is on the hook's blocked-edit list, so regenerate it — never hand-edit it.

Running the script by hand is idempotent and refuses to tag a commit that isn't on `origin/main`, but it is not a dry run — on an untagged version bump it publishes for real.

No dev tool carries a version constraint in `pyproject.toml`. `uv.lock` still pins exact versions and CI runs `uv sync --locked`, so any given build is reproducible — but nothing bounds what the *next* `uv lock --upgrade` pulls in, which means a **linter upgrade can redefine the gate without a line of our code changing**: ruff 0.16 expanded its default rule set (see Error Handling for the `BLE001` fallout) and widened the formatter to Markdown, both of which landed as gate failures on a routine `uv lock --upgrade`. Treat a ruff/ty major as its own reviewable change rather than incidental lockfile noise.

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

## Verifying a dependency upgrade

Four green gates say nothing about `mlx`: every test mocks at the `mlx_lm` boundary, so no test executes a line of the compute library (see Tests). After a `uv lock --upgrade` that moves `mlx`, `mlx-lm`, `transformers` or `huggingface-hub`, run the model by hand against the warm local cache:

```bash
HF_HUB_OFFLINE=1 uv run python - <<'PY' 2>&1 | grep -v ScriptRunContext
import streamlit_app as app
from mlx_lm import load

model, tok = load(app.MODEL_NAME)
text = app.SAMPLE_TEXTS["Product review"]
for lang in (app.LANGUAGE_ENGLISH, "German"):
    for f in app.FEATURES:
        r = app.run_feature(f, text, model, tok, language=lang)
        ok = "prose" if f["output"] == "prose" else ("parsed" if r["parsed"] else "PARSE FAIL")
        print(f"{lang:8} {f['key']:9} {ok:10} {r['raw'][:150]!r}", flush=True)
PY
```

Importing the module in bare mode runs the UI block harmlessly — widgets return defaults and Run is `False`, so nothing infers until the loop calls `run_feature` directly; the Streamlit warnings it prints are expected. **Pass criteria:** all four features return sensible output, **all six JSON runs parse**, and the German run localizes its `rationale` *and* its topic labels into meaningful German while keeping the JSON keys and the `sentiment` enum in English. A German object truncated mid-parse is the specific failure `_effective_max_tokens` exists to prevent, and degenerate-but-parseable labels are the failure the prompt A/B exists to prevent — so read the output, don't just count parses. Cold download and `HF_TOKEN` auth stay unexercised either way; a warm-cache run says nothing about them.

## Dependencies

- `mlx-lm` (pinned `>=0.31,<0.32`) — model loading and generation on Apple Silicon; mlx and transformers are transitive deps. The `<0.32` cap guards against API drift, since decoding params pass through `generate(**kwargs)` rather than typed parameters; exact reproducibility is handled by `uv.lock`.
  - **The cap binds `mlx-lm`, not `mlx`.** mlx-lm declares `mlx` with a floor but *no upper* bound (`mlx>=0.31.2`), so the compute library floats free of the guard above — and since 0.31.3 is mlx-lm's latest release, the cap is not currently binding on anything. As of 2026-08-13 the lock pairs mlx-lm 0.31.3 with mlx 0.32.0, a combination newer than anything upstream shipped together (the mlx-lm sdist predates mlx 0.32.0). That pairing is **verified by real-inference smoke test**, not by CI (re-verified 2026-08-14).
  - The test suite structurally **cannot** cover this. Every test mocks at the `mlx_lm` boundary (see Tests), which is the right call — real inference in CI would mean a 5.2 GB download per run — but it means no test executes a line of `mlx`; the only real contact in CI is the module-level `from mlx import nn`. Hence the hand-run in *Verifying a dependency upgrade*, which is not optional after a move to any of these four packages.
- `streamlit` (pinned `>=1.57`) — web UI. **The floor is now less load-bearing than it reads.** It was argued from the IBM Carbon theme's per-mode `[theme.light]`/`[theme.dark]` blocks, which no longer ship (see Configuration); what is left needing a recent Streamlit is `width="stretch"` and the Material Symbol icons, both of which predate `1.57`. Nothing tests the lower bound — CI installs the `uv.lock` pin — so the floor is kept rather than lowered on the argument that an unverified bound is safer than a guessed one, not because `1.57` is known to be required. Anyone lowering it should check the APIs above against the target version by hand. Exact version pinned by `uv.lock`.
- `python-dotenv` (pinned `>=1.2.2`) — loads `HF_TOKEN` (and other env vars) from `.env` for local development

## Configuration

`pyproject.toml` — ruff lint (`extend-select = ["I"]` turns on isort import sorting atop ruff's defaults; `combine-as-imports`), pytest (`pythonpath`), ty (`python-version = "3.12"`)

`LICENSE` — Apache-2.0 for the project's **code**, declared to tooling in `pyproject.toml` via PEP 639 SPDX fields (`license`, `license-files`) and summarized in the README. The IBM Granite model is licensed separately (also Apache 2.0) and downloaded at runtime, not vendored here.

`README.md`, `docs/images/` — the user-facing README restates facts this file also carries (the model id and its weight sizes, a `granite-4.1-3b-4bit` fallback for smaller machines, the ~16 GB unified-memory envelope, the input precedence, all 12 language names) and embeds `screenshot-dark.png`, whose alt text pins a specific UI state. **No test guards any of it**, so a change to the model, the language list or the layout has to be mirrored there by hand, and a theme or layout change dates the screenshot. A `screenshot-light.png` shipped beside it until 2026-08-14, when removing the IBM Carbon theme dated both; the dark one was re-captured under the built-in dark theme and the light one was dropped rather than re-shot, so the README now carries a single image. To reproduce it — or to add a light counterpart back — capture at **792 CSS px wide × DPR 2** (= its 1584 px) with the toolbar hidden, then crop to **113 px top / 64 px bottom** insets. A full-page capture will not do it on its own: Streamlit scrolls an inner container, so the document stays exactly viewport-tall and `full_page` silently returns just the visible window.

`.python-version` — pins the project interpreter to `3.12` (via `uv python pin`), which `uv sync` / `uv run` honor automatically. Keeps the version you run and test against aligned with the `requires-python = ">=3.12"` floor and the ty type-check target, instead of letting uv auto-select the newest installed Python (e.g. 3.13).

`scripts/gate.sh` — the four Commands in one place, invoked by both CI and the Stop hook. Its header comment argues each point at length; four properties are load-bearing, each pinned by an *executing* test in `TestHooksConfig` because source-level substring checks proved too weak to catch a mutated failure path (see Tests):

- **Exits `2`, not `1`.** Claude Code treats only `2` from a hook as blocking; `1` — what ruff, ty and pytest all actually return — is a *non-blocking* error that lets the turn end on a red gate. Any non-zero fails a CI job, so one convention serves both callers.
- **Reports on stderr**, the stream fed back on a block, while ruff and pytest print diagnostics to stdout. An empty capture (OOM kill, hook timeout, half-created `.venv`) is replaced with a message naming the exit code.
- **Runs every gate even after one fails**, so a single block names everything that is wrong. Claude Code stops honoring a Stop hook after 8 consecutive blocks (raise with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`), and spending that budget one diagnostic at a time wastes it.
- **Skips only a tree that already passed** — a SHA-256 over `git ls-files -co --exclude-standard` against `.git/gate-ok`, written only on green: ~0.09 s for a turn that changed nothing against ~5.2 s for the full run. Every uncertainty runs: an empty file list, a missing memo, a red previous run, a non-empty `GITHUB_ACTIONS`, or `GATE_FORCE`. See the Stop-hook discussion below for why a *content* hash succeeds where `git status` and `stop_hook_active` both failed open.

It also `cd`s to `git rev-parse --show-toplevel` first: `ruff check .` and `pytest` resolve from the working directory, so a caller in a subdirectory would otherwise gate a narrower tree than it believes.

`scripts/release.sh` — cuts the GitHub release when `pyproject.toml`'s version has no tag yet, invoked by ci.yml's `release` job. It is a script rather than inline YAML because an escaped one-liner can't be run or tested, and this one has failure modes worth testing; `TestReleaseWorkflow` pins each property below by executing it with `gh` and `uv` stubbed. Its governing rule is that **every uncertainty is a refusal** — the artifact is a public tag people install, so guessing is never the cheaper option. The header comment argues each of these; what must stay true:

- **The trigger is "no tag exists for this version", not "pyproject.toml changed in this push".** A diff-based trigger has no correct answer to *changed since what?* (`github.event.before` is all-zeros on a branch's first push, a squash-merge rewrites the range, a re-run sees no diff at all), while the tag lookup makes re-runs, force-pushes and manual invocations converge. Exits `0` both when it releases and when there is nothing to release; plain `exit 1` on failure, **not** gate.sh's `2` — that 2 is a hook contract and this is not a hook.
- **The probe is `git/ref/tags/<tag>` (singular), and only a definite 404 may proceed.** The plural `git/refs/tags/<tag>` prefix-matches — verified against the live API, it returns **200** for `v0.1` off the existing `v0.1.0`, so a bump to `0.1` would report itself already released and silently never ship. It must ask the *remote* (the depth-1 checkout has no tags to find), and since a rate limit, an expired token and a 5xx all fail identically to a 404, the script matches `(HTTP 404)` in the response rather than trusting the exit status.
- **Draft first, publish second — then adopt, never duplicate.** The tag comes into existence only at publish, so nothing can leave a tag with no release — which the probe would read as "already released" and skip **forever, silently**. The symmetric hazard is real and was initially documented wrong: GitHub *accepts* a second draft for the same `tag_name` (a draft has no tag to collide with), so a failed publish does **not** fail loudly next time — it would leave two drafts racing for one tag, `gh release edit` resolving whichever it found first. The script therefore lists drafts before creating and adopts an existing one, retargeting it to *this* run's commit.
- **The version comes from `uv version --short`**, a real TOML read rather than a regex. `--short` is load-bearing (bare `uv version` prints `<name> <version>`; before uv 0.7 it printed uv's *own* version, now `uv self version`). The guard rejects any character with no business in a tag, not merely a bad leading one — a first-character-only test admits `0.1.0 (from pyproject.toml)` and would tag it verbatim, spaces and all.
- **A hand-run off `main` is refused.** Unless `GITHUB_ACTIONS` is exactly `true`, the target must be an ancestor of `origin/main`: outside Actions the workflow's `if:` is not in play and `HEAD` is whatever branch the caller is on, so a local run could publish a public tag pointing at an unreviewed commit. Inside Actions the workflow has already made that guarantee, and `origin/main` may not even be fetched at depth 1.

`--target` is `$GITHUB_SHA` (falling back to `HEAD`), so the tag lands on the commit the gate actually validated rather than on whatever the branch drifted to mid-run; an unresolvable commit is an error, because `gh` reads an empty `--target` as "use the default branch". Both `gh` and `uv` are checked for up front so a missing one is named instead of surfacing as a mis-attributed "could not read a version". It `cd`s to the repo root like gate.sh, since `uv version` reads `./pyproject.toml` and `gh` infers the repository from the working directory's remote unless `GH_REPO` is set (the workflow sets it) — and that anchoring block is duplicated rather than shared: extracting it would mean editing a Stop hook whose own failure path is separately pinned, for twelve lines.

Neither script is shellchecked by any gate — `scripts/gate.sh` runs four Python gates and reads no `.sh` file. Both were run through `shellcheck` and `actionlint` by hand; if that matters going forward it needs to become a fifth gate, not an assumption.

`.github/workflows/ci.yml` — GitHub Actions CI, two jobs. `check` runs `scripts/gate.sh` under `uv sync --locked` on every push to `main` and pull request, on a `macos-26` (Apple Silicon) runner — required, since `mlx`/`mlx-metal` are `sys_platform == 'darwin'` in `uv.lock` and `streamlit_app.py` imports `mlx` at module top, so a Linux runner couldn't even collect the tests. The label must stay inside `TestCIWorkflow.APPLE_SILICON_RUNNERS` (`macos-latest` / `macos-15` / `macos-26`) — an explicit **allow-list**, not a glob or a `>= 14` floor: that form is what stayed green on `macos-14` right through the image's deprecation, and it admits the x64 `macos-*-intel` / `macos-*-large` labels where the arm64-only mlx wheels don't install at all. When an image retires, move the label and the allow-list forward together; don't widen it back into a floor. Both jobs pin `actions/checkout@v7` and the **full** `astral-sh/setup-uv@v10.0.0` — setup-uv publishes no major or minor tags from v8 on, so `@v10` does not resolve. `release` then runs `scripts/release.sh`, `needs: check` (a tag never points at a red build) and `if: push && refs/heads/main` (a pull request, including a fork's, can't release — the version bump has to land first). It sits on `ubuntu-latest`, which is fine precisely because it only reads a TOML field and calls the GitHub API, never importing `mlx`. Workflow permissions are `contents: read`; **only** the release job widens to `contents: write`, keeping the job that executes a fork's code unable to push a tag. Its `concurrency` group never cancels in flight — cancelling can land between the draft and the publish, stranding a draft that blocks every later release. `TestCIWorkflow` and `TestReleaseWorkflow` guard this config against drift.

`.claude/settings.json` — project-shared Claude Code hooks: `ruff check --fix` on each edited `.py` followed by `ruff format` on `.py` **and** `.md` (lint is a no-op on Markdown; the `.md` branch exists because ruff ≥ 0.16 made doc snippets a formatted artifact CI enforces), a guard blocking edits to `.env` / `.env.*` (the committed `.env.example` is exempt so the template stays editable) / `secrets.toml` / `uv.lock`, and `scripts/gate.sh` on Stop. Personal overrides go in the gitignored `.claude/settings.local.json`.

Both hooks parse their payload with **`jq`**, an undeclared dependency that nothing installs. macOS 26 ships it at `/usr/bin/jq`, which is why this has never bitten — but if it is missing the guard **fails open**: `jq` not found writes to stderr and exits `0`, and the `.env` edit proceeds (verified). The guard is scoped `Edit|Write|MultiEdit` and does not cover `Bash`, so it is an accident guardrail, not a security boundary — its own message says so.

**Lint-fix runs before format, and the order is load-bearing** — it is ruff's own documented arrangement, for a reason that bites here specifically: `ruff check --fix` can *produce* unformatted code, and the formatter is what cleans it up. Deleting a module's last import (`F401`, a default rule) strands the two blank lines that followed it, so format-then-fix leaves a file starting `\n\ndef …` that `ruff format --check` rejects. That was the shipped order, and its failure was silent in the worst way: `ruff check --fix` exits `0` when it fixed everything, so the hook reported success and handed the Stop gate a formatting failure on a file it had just declared clean. Verified against ruff 0.16.2 — reversing the two is the whole fix.

Both commands run **even when the first fails**, accumulating into an `rc` rather than exiting early, for the same reason `gate.sh` runs every gate: one report should name everything that is wrong. Under the old early-exit form a `ruff format` failure skipped the linter entirely, and putting lint first without this would have let an unfixable lint error leave the file unformatted too — trading one dropped gate for another. Each command still checks its own exit status separately; chaining them so one status is discarded silently swallows `ruff format` I/O errors.

The format hook exits `2` on ruff failure for both extensions. On `PostToolUse` that does **not** block the edit — the tool has already run and the event cannot block — it only guarantees the diagnostic reaches Claude, which a bare exit `1` does not, since ruff writes to stdout and only stderr is fed back. Note that no literal `exit 2` survives in the command (`rc=2` … `exit $rc`), which is why `TestHooksConfig` pins that contract by *running* the hook rather than grepping it.

The Stop hook skips the gate only when re-running it is **provably redundant** — when every file the gate reads is byte-identical to a tree that already passed (mechanism in the memo bullet above).

Two cheaper short-circuits were tried first and both **failed open**, because each inferred "nothing to check" from a *proxy* rather than from the gate's inputs: an empty `git status --porcelain` skipped exactly the turns that had just *committed* work (committing clears dirtiness without clearing risk, and a held `index.lock` disabled the gate outright), and honoring `stop_hook_active` made it one-shot — it blocked once, then let the next Stop through without re-running anything, never verifying its own fix. (That flag is the right guard for a hook that *injects* work and the wrong one for a hook that *verifies*; the built-in 8-block cap already bounds the loop.)

A content hash has neither shape: committing does not alter file *content*, so skipping is correct, and nothing is recorded on a red gate, so it re-runs until green and verifies its own fix by construction. It also beats the tempting marker-file variant (PostToolUse writes "dirty", Stop reads it), which fails open on every edit that bypasses a tool hook: `sed -i`, `git checkout`, applying a patch.

Every uncertainty runs the gate, and two details are load-bearing:

- **An unreadable tree must not fall through to `shasum` of nothing.** That is `e3b0c442…`, a stable *non-empty* hash that could match a stored one — verified: running the fingerprint outside a git repo produces exactly it. An empty file list is therefore a refusal, not an answer, and the pipeline is `</dev/null` so `xargs` cannot block if it invokes `shasum` with no arguments.
- **The memo is recorded *after* the run, not before.** Every gate command goes through `uv run`, which silently re-locks, so `uv.lock` can differ by the time the gates finish; storing the pre-run hash would never match the tree the next Stop sees and the memo would never once hit.

CI never skips — `GITHUB_ACTIONS` disables the *skip*, not the memo, which is still written on green (which is precisely why a cached workspace could carry one back). `GATE_FORCE=1` forces a full run by hand.

**No `.streamlit/config.toml`** — the app uses Streamlit's **built-in light and dark themes**. There is no `base = "default"` to select them: a custom theme is opt-in via a `[theme]` section, so declaring none is what leaves *both* built-ins selectable from the settings menu. That makes the invariant an **absence**, and `TestThemeConfig` asserts the absence of the *section*, not of the file — config.toml may legitimately return for non-theme options (server, logging, client). A lone `[theme]` block (no `[theme.light]` / `[theme.dark]` beside it) would lock the app to one mode and drop the toggle **silently**, since Streamlit only ever *warns* on a theme problem.

The custom theme that shipped until 2026-08-14 (IBM Plex Sans/Mono over IBM Blue 60 `#0f62fe`, Carbon White / Gray 100 per mode) carried a second guard worth keeping in mind if one ever returns: it cross-checked every key against `streamlit.config.get_config_options()`, because a mis-cased key like `backgroundcolor` disables that style with no error. What survives the removal is the one theme-shaped risk the built-ins don't retire — `_SENTIMENT_COLOR`'s four hues must be **built-in Streamlit color names**, since `:teal[…]` is not an error but literal punctuation on the page.

### Environment

`load_dotenv()` runs at the top of `streamlit_app.py`, before `load_model()` contacts the Hugging Face Hub.

- `HF_TOKEN` — optional Hugging Face access token (read scope). The Granite model is public, so it is not required; without it the HF Hub logs an "unauthenticated requests" warning and applies lower rate limits / slower Xet downloads.
- **Local**: set `HF_TOKEN` in `.env` (gitignored; copy from the committed `.env.example`). Loaded automatically by `python-dotenv`.
- **Deploy**: set `HF_TOKEN` as a real environment variable / platform secret. `load_dotenv()` does not override existing env vars and no-ops when no `.env` is present, so the same code works in both environments without shipping `.env`.

- `MAX_INPUT_TOKENS` — optional integer input-token budget (default `16384`, clamped to `MODEL_MAX_TOKENS = 131072`). Resolved once at import by `_resolve_max_input_tokens()` (non-integer, zero, or negative → default, so a sign typo can't silently cap input to one token). Raising it increases context but also memory (~160 KB KV cache/token) and prefill latency, so the default stays conservative and larger-RAM Macs opt into more. Set the same way as `HF_TOKEN` (`.env` locally / real env var on deploy).

## Architecture

`streamlit_app.py` — single-file app. Single-shot flow: one input → run the selected features → show results. Streamlit's built-in light/dark theme (no `.streamlit/config.toml`; see Configuration), native components, Material Symbol icons, no sidebar.

### Model

```python
from mlx_lm import generate, load

model, tokenizer = load("mlx-community/granite-4.1-8b-4bit")
```

`load_model()` is called lazily inside the Run handler (not at module import), so importing the module — e.g. in tests — does not load the ~5.2 GB model.

### Constants

- `MODEL_NAME` — `mlx-community/granite-4.1-8b-4bit`, a 4-bit (affine, `group_size` 32) MLX conversion of `ibm-granite/granite-4.1-8b`: ~5.2 GB of weights vs ~16.8 GB for the bf16 build, at identical architecture, context, and tokenizer. Quantization touches weights only, so the ~160 KB/token KV cache is unchanged. `…-8b-8bit` (~9.4 GB) and `…-8b-bf16` (~16.8 GB) are the higher-fidelity swaps for larger Macs; the README carries the machine-side envelope (~16 GB unified memory) and a `granite-4.1-3b-4bit` fallback for smaller ones.
- `MODEL_MAX_TOKENS = 131072` — Granite 4.1's 128K context ceiling; configured caps are clamped to it.
- `MAX_INPUT_TOKENS` — input-token budget; inputs longer than this are truncated (with a warning) before analysis. Defaults to `16384`, overridable via the `MAX_INPUT_TOKENS` env var (see Environment), resolved by `_resolve_max_input_tokens()`.
- `TEMP = 0.0`, `REPETITION_PENALTY = 1.2` — fixed decoding params. `temp=0.0` is greedy/deterministic (`make_sampler` returns argmax), which keeps the JSON-emitting features reliably parseable; `top_p` is left at its default since it has no effect under greedy decoding. The repetition penalty is applied to **prose only** (it would fight the repeated structural tokens JSON requires).
- `FEATURES` — `list[dict]` registry; each entry has `key`, `label` (toggle), `tab_label` (result tab), `icon` (the result tab's Material Symbol shortcode, e.g. `:material/mood:`), `help` (toggle tooltip), `output` (`"prose"` or `"json"`), `max_tokens`, `system`, and `user_template` (formatted with `{text}`). JSON entries additionally carry `localized_field` — the phrase naming that feature's own free-text value (`"every topic label"`, `"the rationale text"`) that `language_directive` drops into the prompt. It lives in the registry rather than as a branch inside `language_directive` so a new feature can't inherit another's field name; `language_directive` indexes it directly, so omitting it raises a `KeyError` instead of instructing the model to translate a field the schema lacks. `TestFeatures` also checks the phrase names a field the feature's own schema declares.
- `LABELS` — `{key: label}` derived from `FEATURES`.
- `SAMPLE_TEXTS` — `{name: text}` built-in samples for the Sample tab.
- `LANGUAGES` — the **Output language** selectbox list (13 entries): the `LANGUAGE_AUTO = "Match input"` sentinel (the default, not itself a language), followed by Granite 4.1's 12 officially supported output languages — the first of which is `LANGUAGE_ENGLISH = "English"`. Input is multilingual regardless; this controls output language.
- `_LOCALIZED_TOKEN_MULTIPLIER = 2` — every **non-English** output language (including "Match input") gets `max_tokens × 2` via `_effective_max_tokens`, since localized output costs more tokens than the English-tuned budgets and a JSON feature that overruns truncates mid-object and fails to parse. `max_tokens` is a ceiling, so the headroom is free for short output. This deliberately covers Latin-script languages, not just CJK/Arabic — a `_TOKEN_HEAVY_LANGUAGES` set previously narrowed it to Japanese/Chinese/Korean/Arabic, which held only while the rationale field was (incorrectly) staying English; once `language_directive` was fixed, a localized German rationale overran Sentiment's 128-token budget.

The four features: Summarization (prose, 256 tokens), Topic detection and Intent recognition (JSON, 256 tokens), Sentiment (JSON, 128 tokens). The three JSON features share **`_JSON_SYSTEM`**, one module-level template each formats with its own schema — IBM's "answer in JSON … `<schema>`" pattern reproduced verbatim, trailing newline included. Output is not guaranteed JSON, so it is parsed defensively.

> **Design decision (2026-08-12):** `language_directive`'s JSON wording was settled by an A/B of five phrasings against the live model (greedy decoding, so single runs are deterministic), scored on Japanese topic labels and rationale localization. Two independent variables emerged. **Clause order** decides whether `rationale` localizes at all: both candidates ending on the keep-English clause left it in English; all three ending on the localize clause localized it. **Quoting the field name** wrecks topic labels: `each topic "label"` collapsed them into meaningless katakana (`メーマイファーション`), while the otherwise-identical unquoted `every topic label` produced clean output — the quotes appear to read as a literal string to emit rather than a field to translate. Shipped: exception first, requirement last, field named unquoted. A knock-on: once the rationale actually localized, a German one overran Sentiment's budget and truncated mid-object — see `_LOCALIZED_TOKEN_MULTIPLIER`. Don't "simplify" this wording without re-running the A/B.
>
> A follow-up A/B (same day) tried to remove what looks like dead weight: all three JSON features are told to "keep enumerated values (such as the sentiment label) in English", but only Sentiment has an enum, and in the Topics prompt the word *label* collides with the field being localized. **Both** feature-aware replacements — a keys-only clause where no enum exists, in two phrasings — collapsed Japanese topic labels into meaningless katakana (`モーロウングイス`, `ビルグイングイン`) while leaving German *better*. The clause is load-bearing for non-obvious reasons and was kept verbatim on all three features. Note the automated scorer passed all three candidates: its "is it localized?" check was a CJK codepoint test, and degenerate katakana is still CJK. Any future A/B here needs a meaningfulness check, not just a script check.

> **Design decision (2026-06-05):** Granite's native tool-calling (`tools=` → `<tool_call>` blocks) was evaluated as an alternative structured-output channel for the classification features and **rejected**. An A/B over a 55-case adversarial corpus showed no benefit — schema-valid **53/53 tied**, accuracy **45 vs 44** (noise), diverging only on prompt-injection where tool-calling was marginally *worse*. The uniform JSON-prompt approach was kept; don't re-litigate without a material model/task change. **Caveat (2026-08-12):** those are **bf16-era figures**, the baseline a re-run would compare against — they have not been re-measured on the 4-bit default now shipped. The 4-bit evidence is weaker: 12/12 parses across the built-in samples plus 12 more across Japanese/German/"Match input", which is not the adversarial corpus. Re-run the corpus before citing 53/53 as evidence about the shipped model.

### Session State

`st.session_state.results` — `dict | None`. Set on Run to `{"order": list[str], "data": {key: {"raw": str, "parsed": dict | None}}, "truncated": bool, "signature": (input_text, toggles, language)}`; `None` before the first run. Persists across reruns; the `signature` lets the results panel flag when the live input/toggles/language differ from the run. Both the stored and live signatures are built by `_run_signature(input_text, enabled, language)` so the two sides can't drift.

### Layout

A full-width input section sits on top; below it the page splits into two columns (`st.columns(2)`).

- **Input** — `st.tabs(["Text", "Upload", "Sample"])` (each label prefixed with a Material Symbol icon); the active input is resolved by precedence **Text > Upload > Sample** (first non-empty). The uploader accepts `.txt` and `.md` only (`type=["txt", "md"]`) and decodes with `errors="replace"`, so undecodable bytes become U+FFFD rather than raising. Directly beneath the input (full-width, above the column split) is the **Output language** selectbox (`LANGUAGES`, default "Match input"), width-constrained to ~1/3 via `st.columns([1, 2])` — it's a global setting, so it sits with the input rather than in the per-feature column.
- **Left column** — a "Features" subheader over the four `st.toggle` widgets (default on; each description in its `help=` tooltip), with the full-width **Run** button beneath (a `:material/play_arrow:` icon; `width="stretch"`; disabled until there is input and at least one feature is on).
- **Right column** — fixed result tabs: `JSON` plus one tab per feature, derived from `FEATURES` (each feature label composed as `icon` + `tab_label`; the `JSON` tab carries an icon too). JSON shows the combined output; each feature tab renders its result (guarded by try/except), a "not enabled for this run" note if it was off, or a run prompt before the first run. An "Inputs changed since this run — click Run to refresh." note appears when the live input/toggles/language differ from the run. Rendered from `st.session_state.results`.

Interactive widgets carry stable `key=`s so `AppTest` can address them by key rather than positional index: `paste` (text area), `upload` (file uploader), `sample_select` (sample segmented control), `feature_<key>` (per-feature toggles, e.g. `feature_summary`), `language` (output-language selectbox), and `run` (the Run button).

### Functions

- `load_model() -> tuple[nn.Module, TokenizerWrapper]` — loads model and tokenizer via `mlx_lm.load`, cached with `@st.cache_resource`.
- `truncate_to_tokens(text, tokenizer, max_tokens=MAX_INPUT_TOKENS) -> tuple[str, bool]` — truncates to a token budget; returns `(text, was_truncated)`.
- `parse_json_output(raw) -> dict | None` — returns the first JSON **object** found anywhere in the string (tolerates surrounding prose/code fences via `JSONDecoder.raw_decode`) — **including the first object nested inside a top-level array**, since the whole-string fast path returns only on a `dict` and everything else falls through to a scan for `{`. Only input containing no parseable object (scalars, arrays of scalars, unparseable text) returns `None`.
- `resolve_input(pasted, uploaded, sample) -> str` — resolves the active input by precedence (pasted > uploaded > sample); each candidate is stripped first, so a whitespace-only entry falls through.
- `language_directive(feature, language) -> str` — clause appended to the **user** turn telling the model which language to answer in. Localizes only free-text *values* (summary prose, rationale, topic labels); JSON keys and enums (e.g. the sentiment label) stay English so `parse_json_output` / `render_result` keep working. Returns `""` for `"English"`; `"Match input"` mirrors the analyzed text's language. Three wording choices are load-bearing and were each settled by an A/B against the live model (see the design decision below): the keep-English exception comes **first** and the localize requirement **last**; the JSON branch names the feature's own field (rationale / topic label) rather than "all free-text field values"; and that field name is **unquoted**. The prose branch also forbids notes about the language used, which otherwise leak in as a trailing English aside.
- `_effective_max_tokens(feature, language) -> int` — the feature's `max_tokens`, doubled for every non-English language (see `_LOCALIZED_TOKEN_MULTIPLIER`); the base budget for English.
- `run_feature(feature, text, model, tokenizer, language=LANGUAGE_AUTO) -> dict` — builds `[{"role": "system", …}, {"role": "user", …}]` (system prompt verbatim; the user turn carries the `language_directive`), renders it with `tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)`, and passes that string to `mlx_lm.generate` with `_effective_max_tokens(feature, language)`, `make_sampler(temp=TEMP)`, and — **for prose only** — a `make_logits_processors` repetition penalty (`logits_processors=None` for JSON). No "thinking" mode. Returns `{"raw": str, "parsed": dict | None}` (`parsed` only for JSON features).
- `_run_signature(input_text, enabled, language) -> tuple` — the run's identity `(input_text, toggle states, language)`; built on Run and recomputed live so the results panel can flag stale results. Single source so build/compare sides can't diverge.
- `render_result(key, result) -> None` — renders one feature's result with native components: prose for summary; a dataframe for topics (confidence as a `ProgressColumn`); `st.metric` for intent/sentiment, each with an optional rationale and a percent-formatted confidence (`_render_confidence`). The sentiment value is color-coded by enum (`_SENTIMENT_COLOR` → `:color[…]` markdown, which resolves Streamlit's **built-in color names** against the active theme — positive→green, negative→red, neutral→gray, mixed→orange; an unrecognized name is not an error, it renders as literal punctuation, which is what `TestThemeConfig` pins), matched **case-insensitively** (`.lower()`, so `"Positive"` still colors); an out-of-enum label renders uncolored. Untrusted model output is guarded — `topics` that is not a **non-empty** list falls back to a message, `st.metric` values are coerced to strings, and JSON parse failures show the raw response.

### Performance

The load-bearing choices are stated where they are defined — lazy `@st.cache_resource` model load (Model), the `MAX_INPUT_TOKENS` truncation budget and greedy decoding (Constants). One decision has no other home:

- No `@st.fragment`: the one expensive op (inference) is already gated behind Run and `@st.cache_resource`-cached, so isolating reruns would add complexity for no gain — and a results-panel fragment would not even see the input/toggle/language widgets it depends on (they live outside it), breaking the cross-widget staleness note. `st.session_state.results` is initialized with `st.session_state.setdefault`.

### Error Handling

Unexpected exceptions during a run — and during per-feature rendering — are shown with `st.exception()`. JSON parse failures degrade gracefully to the raw response, and `render_result` guards/coerces untrusted model output before passing it to `st.metric` / `st.dataframe`.

Both of those `except Exception` handlers carry an inline `# noqa: BLE001` naming their role (top-level run guard / untrusted model output shape). `BLE001` ("do not catch blind exception") entered ruff's **default** rule set in 0.16, and it is right about blind catches in general — but these two are deliberate UI boundaries: a Streamlit script has no frame above it to catch anything, so an escaped exception blanks the page instead of showing the user what broke. The suppression is per-line rather than a project-wide `ignore` in `pyproject.toml` **on purpose** — the rule stays live, so a third, *unintentional* blind catch added later still fails the lint gate.

## Tests

`tests/test_streamlit_app.py` — unit tests (mocked, no model download). Data-driven cases use `@pytest.mark.parametrize` (each `pytest.param` carries an `id=` so failures are self-labeling); `TestRunFeature` shares a `tokenizer` fixture:

The suites that assert by *executing* a shell script (`TestReleaseWorkflow`, `TestHooksConfig`) share a **session-scoped `stub_bin` fixture**, and that is a performance contract, not tidiness. macOS scans every newly created executable the first time it runs — measured here at **241 ms**, against **4 ms** to re-run one already scanned *or to run it through a fresh symlink* (the scan is keyed to the inode, so a symlink into a fresh directory is free). Writing throwaway `gh`/`uv` stubs per test therefore cost ~17 s of a 21 s gate, paid again on every Stop hook, with essentially none of it spent on the tests' own logic. So the stubs are written once and varied through `$STUB_*` **environment variables** rather than by regenerating their source, and `release.sh` / `gate.sh` are **symlinked** into the throwaway repo instead of copied (both locate their root from the *working directory* via `git rev-parse --show-toplevel`, so a symlink resolves the same tmp repo a copy did). Tests still get a private bin directory with only the tools that case wants symlinked in, which is what keeps `omit=` honest — a tool left out stays genuinely unreachable rather than merely unstubbed. Net: pytest 19.7 s → 4.8 s, with mutation coverage re-verified unchanged. If a future stub needs per-test *behavior*, add an environment variable — do not go back to writing a file per test.

Logging argv is what makes `create < publish` assertable at all, and what pins `uv version --short` — the stub returns the same string with or without the flag, but production does not. The log also covers the exact-match ref probe, `--target`, `--generate-notes` and the `v<version>` title; separate cases cover the already-tagged no-op, draft adoption instead of duplication, and the refusals (inconclusive probe, unlistable releases, unreadable/implausible version, unresolvable commit, off-main hand-run, missing `gh` or `uv`). Two assertions are deliberately narrower than they look: the failed-publish case asserts `"publish or delete the draft"` rather than `"draft"` (which the *create*-failure message also contains) and the missing-tool case asserts `"<tool> is required"` rather than the bare name (which `sh`'s own "not found" supplies) — both were caught surviving mutation as the looser form. All 18 plausible mutations were verified to turn the suite red
